## 对上一轮要求的修正

上一份沟通文件中写“ccc/c/黑白蓝点未确认，不得猜测”，表述过于保守，容易让 GLM 误以为这些标记完全不能解释。

正确的要求是区分两层：

1. 爱五子棋软件中的实际显示约定和用户可理解语义。
2. RenLib 二进制格式中原始字节或字段的正式标准含义。

即使目前还不能证明某个字节在 RenLib 标准中的正式命名，也可以按照已经观察和确认的爱五子棋使用约定来显示。

## 当前应采用的实际语义映射

根据之前对爱五棋打谱体验和用户观察的总结，先按以下语义层处理：

| 爱五子棋显示内容 | 当前实际语义 | 网页建议显示 | 备注 |
|---|---|---|---|
| a | 胜点 / 好点 / 推荐变化 | 好点或胜点 | 不要显示成普通无意义字母 |
| c | 败点 / 坏点 / 不推荐变化 | 败点或坏点 | 用户已经明确指出 c 是败点约定 |
| ccc | 通常视为 c 类败点信息的重复或编码表现 | 败点，不应大量显示为 ccc 文本 | 需要继续查明它为什么被解析成 ccc |
| 黑色点 | 可以走、可行或推荐的后续点 | 黑色后续点 | 按爱五棋视觉约定 |
| 白色点 | 败点、错误或不推荐的后续点 | 白色败点 | 按爱五棋视觉约定 |
| 蓝色点 | 另一类特殊变化或状态 | 蓝色特殊点 / 未知类别 | 语义仍需通过更多样本确认 |

## 重要边界

以上是“爱五棋里的实际显示语义”，不是已经证明的 RenLib 官方字段标准。

因此实现时必须同时保存两份信息：

### 原始信息

例如：

- raw mark byte；
- raw text；
- raw color/status code；
- 原始节点 ID；
- 原始节点层级。

### 解释信息

例如：

    semantic: "good" | "bad" | "special" | "unknown"

或：

    displayKind: "recommended" | "losing" | "special"

这样以后如果发现某个 RenLib 版本的 c 或颜色含义不同，可以调整解释层，不需要重新解析和破坏原始数据。

## 对 ccc 的具体要求

不能继续简单地把大量 ccc 当成正常 boardText 展示。

应按以下顺序处理：

1. 检查 ccc 是否来自 RenLib 原始文本。
2. 如果原始文本就是 ccc，将其归类到 c 类败点语义，并显示简洁的“败点”或败点样式，不在棋盘上重复叠加 ccc。
3. 如果 ccc 是游标错位、编码错误或控制字节错误产生的，则修复解析器，不要在 UI 层打补丁。
4. 如果一条记录同时有落子和 ccc 标记：
   - 已落子位置不再显示文字标签；
   - 败点语义应显示在对应的后续空位；
   - 不应把 ccc 挂到当前已落子的棋子上。
5. 如果没有足够信息确定对应位置，保留 rawText，但在 UI 中以“未知 RenLib 标记”处理，不能凭坐标猜测。

## 对 a/c 的具体实现建议

建议不要把 a 和 c 直接丢进普通 boardText，而是增加一个解释层：

    type RenLibSemantic = "good" | "bad" | "special" | "unknown";

    interface RenLibAnnotation {
      rawText?: string;
      rawMark?: number;
      semantic?: RenLibSemantic;
      displayText?: string;
      displayColor?: "black" | "white" | "blue" | "neutral";
    }

映射第一版可以是：

    a -> { semantic: "good", displayText: "好点" }
    c -> { semantic: "bad", displayText: "败点" }
    ccc -> { semantic: "bad", displayText: "败点" }

但必须保留 rawText，不能只保存转换后的中文。

## 对黑白蓝点的具体实现建议

变化点和评价点必须分开：

- 黑色点：表示爱五子棋约定中的可行 / 推荐后续。
- 白色点：表示爱五子棋约定中的败点 / 不推荐后续。
- 蓝色点：表示特殊类别，暂时使用蓝色视觉，不强行显示成好点或败点。
- a/c 文字语义优先于颜色语义；若两者冲突，应同时保留原始信息并在调试信息中记录冲突。

不要再把所有后续 move 默认渲染成同一种 black/white。应让解析后的每个变化节点携带 displayKind 或 semantic。

## 测试要求

GLM 下一轮必须新增语义层测试：

1. a 解析为 good。
2. c 解析为 bad。
3. ccc 不再作为大量普通文字标签显示。
4. 黑色点显示为可行 / 推荐样式。
5. 白色点显示为败点样式。
6. 蓝色点保留特殊样式。
7. 已落子点不显示重复标签。
8. rawText 和 semantic 同时保留。
9. 未知文本不被强行归类。
10. 导出再导入后 rawText 不丢失。
