## 根据结果立即分流

### 情况 A：importDiagnostic.hasCompact 为 false

说明问题在：

- Worker 没生成 compact；
- 文件没有被识别为大型 LIB；
- Worker 消息没有携带 compactIndex；
- 解析/构建在 Worker 中失败；
- 测试使用了错误文件或错误导入路径。

必须检查：

- 松月文件扩展名和大小判断。
- Worker postMessage 内容。
- compactIndex.nodeCount。
- compactDiagnostic 是否由实际 index 生成。
- App parseRecordFile() 是否收到 compactIndex。

### 情况 B：importDiagnostic.hasCompact 为 true，但 branchDiagnostic.hasCompact 为 false

说明问题在 App 文档绑定、保存/恢复或打开路径：

- ImportResult.compactIndex 丢失。
- lazy document 没有由 compactIndex 重建。
- duplicate/fingerprint 路径打开了旧普通 document。
- IndexedDB 恢复走了旧格式。
- document/nodes 替换后 compact info 丢失。
- 测试没有等待导入完成就调用诊断。

必须在导入后、保存前、保存后、打开后分别输出 source 和 nodeCount。

### 情况 C：两者 hasCompact 都为 true，但 firstBranchId 为 null

说明 compact 索引或 RenLib 父子关系本身有问题：

- childCount 不可信。
- firstChild/nextSibling 链断裂。
- DOWN/RIGHT 解析错误。
- 真实文件的分支记录未进入索引。
- 分叉扫描只扫描了错误的 node range。

此时必须先做 index 层和解析层修复，不能继续改 UI 断言。

### 情况 D：两者 hasCompact 为 true，firstBranchId 非空

这才进入 UI 强验收：

- 直接跳转 firstBranchId。
- 打开变化面板。
- 验证文案总数等于 firstBranchChildCount。
- 验证真实分支行数大于 0。
- 验证首行坐标。
- 点击第二个兄弟分支。
- 验证 currentId 和最后一手坐标变化。
- 跳到该分支叶节点，验证还能看到兄弟变化。

## 关于测试实现

如果当前 App 没有可靠的页面跳转接口，增加测试专用调试接口：

    window.__banbuJumpToNode(nodeId)

要求：

- 只读/调试用途。
- 不影响普通用户界面。
- 调用后更新 currentId。
- 返回当前 nodeId。
- QA 调用后等待棋盘和状态文本更新。

同时建议增加：

    window.__banbuGetBranchSnapshot()

返回：

    {
      currentId,
      pivotId,
      totalChildren,
      visibleChildren,
      visibleChildIds,
      visibleChildCoordinates
    }

这样测试不依赖脆弱的文字定位器。
