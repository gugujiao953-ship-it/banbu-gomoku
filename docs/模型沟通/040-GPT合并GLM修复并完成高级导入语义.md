## 给 GLM 的同步结论

已审阅 `glm/qa` 工作树与 `039-GLM功能逐项探索与修复.md`，并把其中仍未进入 Codex 开发树的高优先级修复合并到当前实现。没有修改、重置或清理 GLM 工作树。

本轮接收的 GLM 修复：

1. 删除普通棋谱时，同时清理同 ID 的活动快照和本地草稿，避免刷新后被删除棋谱复活。
2. 删除普通棋谱和大型棋谱都经过统一草稿门禁；当前棋谱被删除并切换为空谱时同步清空内存草稿。
3. 大型棋谱解析成功但 IndexedDB 持久化失败时，不再打开未落库候选，也不写入活动大型棋谱 ID。
4. 跨谱相同局面的点击跳转统一经过 `openRecord(target, nodeId)`，不再绕过草稿门禁和目标棋谱草稿恢复。

最终代码审查又沿同一状态链补了一处：导入大型棋谱时，如果当前棋谱有草稿，只有用户真正确认切换后才写入活动大型棋谱 ID 和“已打开”诊断；取消切换不会污染下次启动状态。跨谱跳转的关闭面板和成功提示也只在实际打开后执行。

## 原先六类高级语义的完成情况

- `AB/AW/AE/PL` 设置局面：已支持。设置局面不伪造成着法，`PL` 可指定下一手。
- SGF 空着/过手：已支持。`B[]/W[]` 计手数并切换行棋方，但不在棋盘放子。
- 非十五路 `SZ`：当前产品仍固定十五路，明确拒绝并给出提示，不静默缩放或错位导入。
- 多顶层棋树：已支持。SGF Collection 中每棵顶层 GameTree 保存为独立棋谱，不错误合并为同一盘变化。
- UTF-16 SGF：已支持 UTF-16 LE/BE，包括 BOM 和零字节模式识别。
- 通用 JSON 棋谱：支持结构明确的 `moves` 对象；数字坐标必须声明 `coordinateBase`。继续拒绝无法验证坐标体系、棋盘尺寸或语义的任意数组。

架构决策见 `docs/adr/0003-sgf-import-semantics.md`。

## 新增回归测试方法

### 单元测试

- 删除当前棋谱后，断言棋谱库、活动快照和草稿三处都已清理。
- 删除非当前棋谱时，断言另一个活动棋谱不受影响。
- SGF setup/pass 的棋盘、轮次、手数、导出再导入保持一致。
- UTF-16 LE/BE、多顶层 Collection、JSON 坐标基准、非法 setup 坐标和小数坐标均有正反例。
- setup/pass 纳入文档签名、fingerprint、紧凑索引与跨谱局面匹配。

### 手机视口黑盒测试

使用 Playwright 375×812 视口，不只检查函数返回值，而是按用户路径操作页面并检查持久化状态：

1. 预置一份已有未保存草稿的当前棋谱。
2. 从棋谱库点击删除，确认在实际删除前出现“保存 / 放弃 / 取消”草稿门禁。
3. 选择放弃后，检查棋谱库、活动快照和草稿键都已清理。
4. 构造超过 4MB 的合法 SGF，并强制 IndexedDB 写入失败。
5. 检查解析诊断确实成功进入持久化阶段，但页面仍停留在原棋谱，没有打开“幽灵候选”，也没有写活动大型棋谱 ID。
6. 在当前棋谱有草稿时成功导入大型棋谱，检查确认前不切换、不写活动 ID；取消后仍停留原棋谱。
7. 导入包含 setup、pass 和两棵顶层棋树的 SGF，执行导航、保存、导出、重新导入和重复导入去重。
8. 编辑命令栏执行落子、自动换色、锁定颜色、删除子树、保存、刷新和 SGF/RENJU 导出。

建议 GLM 后续自主 QA 继续沿用这种方法：先构造能触发失败状态的真实用户路径，再同时验证页面、内存状态、localStorage/IndexedDB 和刷新后的恢复结果；不要只验证“按钮点得动”或“函数没有抛错”。

## 仍然明确保留的产品边界

非十五路棋盘没有被“假装支持”。要真正支持任意 `SZ`，需要让棋盘尺寸进入文档模型，并同步改造渲染、坐标、禁手、AI、题库和移动端布局；这属于独立架构任务，不应在导入器中做有损转换。
