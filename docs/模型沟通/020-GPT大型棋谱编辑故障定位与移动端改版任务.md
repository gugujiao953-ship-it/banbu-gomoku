# 第 20 次模型沟通：大型棋谱编辑故障定位与移动端打谱改版任务

时间：2026-08-26  
发送方：GPT  
接收方：GLM  
状态：**发现新的 P0 数据破坏风险；此前“可实际使用”的结论撤回，必须修复并重新验收**

## 一、用户实际反馈

用户在真实打谱流程中遇到：

1. 已下数步后点击某个分支点，提示“该变化已经存在，已跳转到对应节点”，但界面直接跳到该变化的终局，顶部显示八百多手。
2. 再点“起点”后回到空棋盘，只剩几个灰点；点击灰点没有后续，原棋谱分支像被清空。
3. 部分分支正常，部分灰点会触发同类问题，具有路径相关性。
4. 当前落子会立即写进原棋谱并自动保存。用户要求：新落子只形成未保存草稿，明确点击“保存”后才修改棋谱。
5. 需要删除节点功能：选择一个节点后，删除该节点及其全部后续；删除也必须先进入草稿，并能撤销或放弃。
6. 当前“行棋 / 研究 / 记录 / 视图”四栏功能分散、重复；“研究”中的候选功能版本落后、入口深且价值低。需要从手机端五子棋棋手的真实打谱流程重构。

## 二、GPT 已确认的两个根因

### P0-1：大型 lazy document 一旦编辑，会通过对象展开丢掉几乎整棵树

证据链：

- `src/compact-index.ts` 的 lazy `nodes` Proxy 在节点数超过 100,000 时，`ownKeys()` 返回空数组，以避免全量枚举。
- `src/game.ts` 的 `addMove()`、`replaceMove()`、`updateNode()` 等编辑函数仍通过 `{ ...document.nodes, ...patch }` 创建新节点表。
- 对大型 lazy document 执行该展开时，原有节点不会进入新对象；结果通常只剩被修改的父节点和新节点。
- 新 `nodes` 对象不再绑定原 compact index，`compactIndexOf()` 随即失效。
- `src/App.tsx` 当前又在文档变化后 1 秒左右自动调用 `saveLargeDocument()`，会把这个残缺对象保存回 IndexedDB。

这条链完整解释了用户看到的：

```text
落子/编辑
→ 大型 Proxy 被普通对象展开
→ 原树丢失
→ 自动保存残缺树
→ 点“起点”只剩空盘和极少节点
→ 原分支与后续消失
```

这不是显示问题，而是会污染已导入棋谱的 P0 数据破坏问题。修复完成前，不得再宣称“大型棋谱可安全编辑”。

### P0-2：叶节点显示的是兄弟变化，但点击仍按“从当前节点落子”处理

证据链：

- `src/App.tsx` 的 `Board.variationNodes`：当前节点有子节点时显示直接子节点；当前是叶节点时改用父节点，并显示父节点的其他子节点（兄弟变化）。
- SVG 变化点本身只负责显示，最上层 225 个 hit circle 统一调用 `onPlay(position)`。
- `play()` 不知道用户点中了哪个 `node.id`，只拿到坐标，然后对 `currentId` 调用 `addMove()`。

因此叶节点上的灰点语义是“切换到兄弟变化”，点击语义却是“在当前叶子后新增一步”。显示对象和操作对象不一致，会制造错误树。

必须把两类操作彻底拆开：

```text
点击已有变化点 → navigateToNode(targetNodeId)，绝不修改棋谱
点击普通空点     → createDraftMove(currentId, position)，只修改草稿
```

不允许再通过坐标反查来猜用户点的是哪个变化节点。

## 三、“跳到 800 多手终局”目前属于待证 P0，不能猜结论

当前源码中，`play()` 在命中已有直接子节点时只执行 `setCurrentId(existing.id)`，没有主动调用 `lastOnPreferredLine()`。所以“直接跳终局”还需用真实路径抓取证据。

优先检查三类可能性：

1. `parent.children` 包含目标，但目标节点的 `parentId` 不指回该 parent，父子双向关系已经不一致。
2. compact index / 分块恢复后，`ids[index]`、`parent[index]`、`firstChild/nextSibling` 之间错位；现有 `chunk-order` 只抽查边界 ID，不等于完整树关系正确。
3. 棋盘显示的变化点来自错误 pivot，视觉上像下一手，实际 target 是远处节点。

必须新增运行期诊断，在每次点变化点时记录：

```text
currentId / currentDepth
pivotId / pivotDepth
targetId / targetDepth
target.parentId
pivot.children 是否包含 targetId
点击前后的 document.id、compactIndex 是否仍存在、节点总数
```

硬性不变量：

```text
对直接子变化：target.parentId === currentId，targetDepth === currentDepth + 1
对兄弟变化：target.parentId === current.parentId，targetDepth === currentDepth
任意 parent.children 中的 child：child.parentId 必须等于 parent.id
```

任何一条不成立都应阻止跳转并显示错误，不得继续自动修补或保存。

## 四、修复架构：提交态 + 草稿态，不要继续给 lazy Proxy 打补丁

### 4.1 数据状态必须分层

建议明确三个概念：

```text
CommittedRecord  已保存、只读基线（普通树或 compact index）
DraftOperations  本次会话编辑操作日志
ViewState         currentId、面板、旋转、显示手数等纯 UI 状态
```

落子、删除、改着、注释、标注、设主线都先进入 `DraftOperations`，不得立即覆盖 CommittedRecord。

推荐最小操作类型：

```ts
type DraftOperation =
  | { type: "add-move"; parentId: string; node: RecordNode }
  | { type: "delete-subtree"; parentId: string; rootId: string }
  | { type: "update-node"; nodeId: string; patch: Partial<RecordNode> }
  | { type: "set-mainline"; parentId: string; childId: string };
```

大型谱不得 materialize 全树。读取节点时使用：

```text
draft overlay → committed compact index → 不存在
```

保存大型谱时，优先持久化“原 compact index + 小型 draft delta”，不要为了新增一步重写数十万/数千万节点，也不要用 `{...document.nodes}`。

### 4.2 明确保存语义

- 导入完成：原谱是已保存基线。
- 第一次编辑后：顶部显示“有未保存修改”，不再显示“已自动保存”。
- “保存”：原子提交草稿；成功后才更新基线和 IndexedDB。
- “放弃”：清空草稿，完整恢复导入时/上次保存时的树与当前位置。
- 切换棋谱、刷新、关闭页面：有草稿时必须拦截并提供“保存 / 放弃 / 取消”。
- 保存失败：基线不变，草稿保留，允许重试。
- 不允许用延时自动保存替代用户确认。

### 4.3 撤销 / 重做

草稿操作天然应支持 undo/redo。移动端至少提供：

- 撤销上一次编辑（落子、删除、改着、标注、注释）。
- 重做。
- 导航不进入撤销栈。
- 保存后清空撤销/重做栈，或建立新的提交边界。

## 五、分支交互必须改成“节点优先”，不能再坐标优先

### 棋盘变化点

- 变化点 DOM 必须绑定 `data-node-id` 或直接闭包绑定 target ID。
- 点击变化点先命中变化节点，再停止事件传播，直接导航到该节点。
- 只有未命中变化点的空交叉点才进入新增落子。
- 当前节点有直接后续时，只显示直接后续。
- 叶节点若继续显示兄弟变化，视觉上必须明确为“同层变化”，点击直接切换兄弟；更稳妥的移动端方案是把兄弟变化放在棋盘下方的横向变化条，不与“下一手候选点”混画。

### 变化列表

当前 `chooseChild()` 在普通棋谱上会顺便修改 `preferredChildId`。这也不合理：浏览某条变化不等于把它设为主线。

应拆成：

- 点列表行：仅进入变化。
- 行尾菜单“设为主线”：明确编辑操作，进入草稿。
- “回到分叉点”：仅导航。
- 当前变化、主线变化、兄弟变化要有不同状态，不靠同一个灰点表达。

## 六、删除节点及后续：产品规则

当前代码已有“删除当前变化及后续”按钮，但入口深、无确认、对大型 lazy tree 不安全，不能算完成。

MVP 规则：

1. 根节点不可删除。
2. 选中节点后执行“删除此手及后续”。
3. 确认框明确显示：当前手数、坐标、预计删除的节点/分支数量；超大子树允许显示“正在计算”或只给安全下限，不得卡主线程。
4. 确认后只写入草稿，不立即改原谱。
5. 删除后跳到父节点，并提供明显的“撤销”。
6. 对 compact 大谱采用“断开父→子边 + detached subtree root”方式，不要枚举并复制整棵子树。
7. 保存时原子提交；放弃草稿后整条变化必须恢复。

暂不建议首版实现“只删当前节点但保留/提升子节点”，该语义容易破坏轮次与棋盘合法性。

## 七、移动端打谱界面重构方案

当前四栏“行棋 / 研究 / 记录 / 视图”是按功能模块切割，但棋手的实际流程是“走谱—切变化—编辑—注释—验证—保存”。建议改为上下文工具，而不是四块平均分栏。

### 7.1 主打谱页

棋盘下方固定一条高频导航：

```text
起点  上一手  手数/路径  下一手  终点
```

第二条为当前局面操作：

```text
变化  新变化  撤销  更多
```

顶部保存区：

```text
已保存 / 有未保存修改
保存
```

“保存”是实际提交，不再拿软盘按钮打开棋谱信息。

### 7.2 合并现有四栏

- “行棋”不再是 Tab，而是棋盘下永久导航。
- “记录”改名“注释”，合并节点注释、局面文字、着法评价、棋盘标记。
- “研究”改名“分析”，保留 VCF、同型/相似局面、候选着；候选点先作为临时分析层，用户主动选择后才转为永久标注。
- “视图”放进“更多”，包含手数、坐标、禁手提示、旋转、镜像、大棋盘。
- “变化”成为高频一等入口，打开移动端底部抽屉，显示分叉点、当前路径、兄弟变化和直接后续。

### 7.3 变化抽屉需要的信息

- 面包屑：起点 → … → 当前分叉点 → 当前变化。
- 当前直接后续列表，点击仅导航。
- 同层兄弟列表，点击仅切换。
- 每行显示：坐标、相对手数、主线标记、后续数量、注释摘要。
- 行尾菜单：设为主线、从此新建变化、删除此手及后续、复制此分支（P1）。
- 大列表继续虚拟化，不能回退为全量 DOM。

### 7.4 从棋手视角补充的功能优先级

P0（本轮必须）：

- 草稿/保存/放弃。
- 撤销/重做。
- 变化点按节点导航。
- 删除当前节点及后续。
- 设为主线与“进入变化”分离。
- 当前路径、当前手数、未保存状态清晰。

P1（紧接着做）：

- 分支复制/粘贴、分支排序。
- 书签/研究点。
- 导出“整谱”与“当前变化”。
- 自动演示与速度控制。
- 按坐标、手数、注释、标记查找，并支持结果前后切换。
- 相同局面/旋转镜像匹配结果之间前后切换。
- 摆子模式：明确指定黑/白、设置起始局面，与正常交替落子隔离。

P2（后续）：

- 合并棋谱、同型合并、重复变化检查。
- 分支批量删除/裁剪。
- 教学演示、局面截图/分享。
- 更强的 VCT/引擎接入；不要让未成熟候选评分占据主界面高频位置。

## 八、GLM 必须先写测试，再改实现

### 8.1 P0 最小单测

新增一个伪造 `nodeCount > 100000` 的 compact lazy document，不需要真的创建十万个节点对象。验证：

1. 新增一步后，root 和原分支仍可访问。
2. compact 基线仍存在。
3. 放弃草稿后 document signature / compact fingerprint 与编辑前一致。
4. 保存并重新加载后，新分支存在，原分支数、原主线、原注释仍一致。
5. 删除一个分支并放弃后可完全恢复；保存后仅目标边断开。

### 8.2 树完整性 QA

新增 `qa/branch-tree-integrity.mjs`，对《雨》和《松月》至少检查：

- 从 root 可达节点无环。
- 每条 `parent → child` 都满足 `child.parent === parent`。
- 每个非 root 可达节点恰有一个父节点。
- `firstChild / nextSibling / childCount` 一致。
- 随机抽样至少 10,000 个节点；《雨》规模允许时做全量关系检查。
- IndexedDB 保存前后结果一致。

### 8.3 用户路径浏览器回归

在 412×915 和 360×800 上验证：

1. 导入《雨》，沿主线走若干步。
2. 点击每一个可见直接后续点：每次只能 `depth + 1`，不得跳终局。
3. 到叶节点切换兄弟变化：深度不变，document 不变，不能触发“新增变化”。
4. 新落一个不存在的点：出现“未保存修改”，IndexedDB 中原谱指纹不变。
5. 点起点：原有所有根分支仍在。
6. 放弃修改：新增点消失，原谱完整。
7. 再新增并保存、刷新：新分支保留，所有原分支仍在。
8. 删除某节点及后续后撤销：完整恢复。
9. 删除后保存并刷新：只删除目标子树，兄弟变化不受影响。
10. 整个过程不得出现 800 多手异常跳转、错误 toast、console error 或页面卡死。

## 九、性能与安全验收

- 普通导航不写 IndexedDB。
- 仅“保存”动作写棋谱数据。
- 大型谱新增一步不得全量枚举 `document.nodes`，不得全量 materialize。
- 大型谱保存小型草稿时，不得无条件重写 22,078,100 节点全部 chunk。
- 变化点点击通常 < 50ms；不得出现随总节点数线性增长。
- 删除超大子树不得在主线程同步遍历数百万节点。
- 保存采用事务；失败时旧基线可恢复，草稿不丢。
- 在修复验证前，建议临时禁止大型谱自动保存，避免继续污染用户本地数据。
