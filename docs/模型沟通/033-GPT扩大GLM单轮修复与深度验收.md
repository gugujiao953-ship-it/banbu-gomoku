# 第 33 次模型沟通：扩大 GLM 单轮修复量与深度验收

时间：2026-08-26
发送方：GPT / Codex
状态：立即执行

## 规则变更

本文件覆盖 032 号文件中的“每个 Bug 单独提交”限制。

用户希望 GLM 在一次对话中尽可能多发现问题、修复问题并完成回归，不要发现一个小问题就停止，也不要因为机械拆分提交而降低处理效率。

新的要求是：

- 一次对话可以并且应当持续解决很多问题，越完整越好。
- 不要求一个 Bug 一个提交。
- 可以按一个完整功能域或一组紧密相关问题形成一个提交，例如“保存与分组修复”“注释与标注修复”“大型谱生命周期修复”“移动端布局修复”。
- 一个提交可包含多个相互关联的 Bug、相应测试和必要的体验调整。
- 不要把完全无关、难以独立回退的内容塞入同一提交；但也不要为了提交纯度把一轮工作人为切成几十个小提交。
- 一次对话至少完成“广泛测试 → 汇总问题 → 分组修复 → 全量回归 → 再探索一轮”，不能修完第一个问题便结束。
- 只要时间和上下文允许，应继续寻找下一批问题；没有达到退出条件前不要宣布全部完成。

推荐提交信息：

```text
fix(qa): repair save, folder, and persistence flows
fix(qa): repair annotation and comment interactions
fix(qa): harden large-record edit lifecycle
fix(qa): improve mobile editor usability
```

## 单轮工作节奏

GLM 每次对话按以下循环执行：

1. 先完整体验主要用户流程，不改代码，建立问题清单。
2. 将问题按数据安全、功能错误、性能、移动端体验、视觉细节分级。
3. 优先批量修复严重和高频问题，再处理明显体验问题。
4. 对每组修复增加或更新自动测试。
5. 跑全量门禁，并重新执行真实浏览器流程。
6. 用不同数据、不同入口、不同视口再探索一次，确认没有只修表面症状。
7. 若又发现问题，继续下一轮测试—修复—回归，而不是立刻结束对话。

退出条件：已经覆盖本文件的测试矩阵；严重/高优先级问题为零；中低优先级问题已修复或明确记录原因；所有门禁通过；报告中有真实证据。

## 不要只验证“能点”

每项功能至少验证下面五层：

1. **即时界面**：按钮、棋盘、文字和状态是否马上正确变化。
2. **内存状态**：currentId、documentId、草稿数量、节点关系是否正确。
3. **持久化状态**：localStorage / IndexedDB 中正式记录与草稿是否符合预期。
4. **刷新恢复**：刷新、关闭后重开、从棋谱库再次打开是否仍正确。
5. **交换结果**：导出 SGF / RENJU 后重新导入，结构、注释、标注和分支是否保持。

Toast、按钮变色、没有 console error 都只能作为辅助证据，不能作为通过结论。

## 全流程探索测试矩阵

### A. 新建、导入与切换

- 空白启动、新建棋谱、连续新建多份、重名棋谱。
- 分别导入 SGF、RENJU JSON、小型 LIB、雨.lib、松月.lib。
- 单文件导入、批量导入、重复导入、错误后缀、损坏文件、超限文件。
- 导入过程中点击其他页面、切换模式、快速重复点击导入。
- 棋谱之间来回切换，尤其检查有草稿时保存/放弃/取消三个分支。
- 打谱与做题反复切换后，棋谱 currentId、题目进度和草稿是否串线。

### B. 棋谱树与导航

- 起点、上一手、下一手、终点连续快速点击。
- 主线中间创建分支，分支中再创建多层分支。
- 点击已有棋子跳到对应手，再落子、删除、撤销、重做。
- 点击灰色/黑色变化点，检查是否跳到正确的直接子节点，而不是某条终局。
- 已存在变化时再次下同一点，检查跳转节点、步数和后续分支是否正确。
- 根节点、中间节点、叶节点、兄弟分支位置分别打开变化面板。
- 删除当前一步及全部后代后，检查棋盘、主线、分支数、下一手、导出内容一致。
- 删除后放弃、删除后保存、删除后刷新分别验证。

### C. 草稿、保存和数据安全

- 新增一步、多步、分支、注释、标注、改着、删除分别产生草稿。
- 不点击保存直接刷新：应按产品约定恢复草稿，但不能污染正式棋谱。
- 点击常驻保存、右上角保存、切谱保护弹窗中的保存，结果应一致。
- 保存到不同棋谱文件夹，刷新后分组仍在。
- 另存为题库后，原棋谱草稿必须保持，不能被清空。
- 保存失败、存储空间异常、快速连续保存、保存时立即切谱。
- 普通棋谱、大型原谱、大型派生谱、派生谱二次编辑分别执行同一生命周期。
- 对比保存前后：棋子数、节点数、分支数、currentId、documentId、active summary ID、draft 数量。

### D. 文件夹与棋谱库

- 棋谱和题库分别新建文件夹，测试空名称、空格、重复名称、长名称、中文和符号。
- 创建后立即保存到该文件夹，刷新后再检查。
- 多个棋谱/题集移动到不同分组，来回切换题库/棋谱页。
- 空文件夹、有内容文件夹、未分类状态的展开和折叠。
- 删除棋谱后检查文件夹计数、当前正在打开的棋谱和活动 ID。
- 搜索后移动、打开、删除，确认过滤状态不会指向错误项目。

### E. 标注、变化点和注释

- 文字、圆圈、三角、叉号及每种颜色分别放置、保存、刷新、导出重导。
- 单字、双字、四字、数字、中文标注检查手机清晰度和是否越界。
- 标注在变化点后，底层黑色小圆必须消失，只显示标注。
- 清除标注后，若该位置仍是合法变化点，变化提示应恢复。
- 尝试在已有棋子上放置空点标注：不得覆盖棋子，应转为导航或提示使用注释。
- 对当前手添加、修改、清空多行注释；检查棋子右下角评论图标。
- 展开注释时，下面操作区折叠；再点一次恢复；切换节点后展开状态应复位。
- 注释超长、多行、英文、标点时不应撑破页面或遮挡关键按钮。
- 注释保存在正确节点，上一手/下一手不能错误显示其他节点的注释。

### F. 黑白落子与锁定

- 默认自动换色：黑后白、白后黑，显示与实际落子颜色一致。
- 黑锁定、白锁定、解除锁定后连续下子。
- 导航到奇数手、偶数手、分支中间后解除锁定，颜色应由局面而非旧 UI 状态决定。
- 删除、撤销、重做、切谱、刷新后检查颜色指示。
- 快速点击黑、白、锁按钮以及棋盘，检查滑块区间、选中态和实际落子是否竞争错乱。

### G. 导出与重新导入

- 未保存草稿状态导出与保存后导出分别检查产品语义。
- SGF、RENJU 导出文件必须可重新导入。
- 对比主线长度、总节点、分支结构、注释、局面文字、着法评价、标注样式和颜色。
- 删除变化后导出，已删除子树不能复活。
- 大型棋谱导出期间检查卡顿、下载是否重复、文件名是否合法。

### H. 移动端与体验审计

至少使用 320×568、360×800、375×812、390×844、430×932 五种视口。

- 检查横向溢出、底部安全区、弹窗被键盘遮挡、按钮触控区域小于约 40px。
- 单手操作能否完成上一手/下一手、保存、删除、换色、注释。
- 快速连点、双击、长按、滑动棋盘与滚动页面是否误触落子。
- 底部弹窗打开时背景不能误操作，关闭后焦点和滚动位置合理。
- 长名称、长注释、大字号、窄屏下不能重叠或截断关键内容。
- 不只找功能 Bug，也记录“看不清、找不到、步骤太多、反馈太弱、容易误删、按钮含义不明”等体验问题，并在不改变产品核心语义的前提下直接优化。

### I. 性能与稳定性

- 雨.lib 和松月.lib 记录导入、打开、连续导航 100 手、打开变化面板、保存和导出耗时。
- 记录超过 50ms、100ms、500ms 的长任务。
- 连续导航、反复开关弹窗和切谱后，DOM 数量与内存不应持续增长。
- 大量分支只能渲染可见窗口，不能因为统计或预览隐式展开整棵树。
- 测试浏览器返回/前进、页面刷新、强制停止导入、网络离线和 PWA 缓存后的基本可恢复性。

## 组合与破坏性测试

很多 Bug 只在功能组合时出现。必须额外执行：

- 标注 → 注释 → 新分支 → 删除 → 撤销 → 保存 → 刷新 → 导出 → 重导。
- 大谱导入 → 中间节点创建三步 → 切谱取消 → 再切谱保存 → 刷新 → 二次保存。
- 新建文件夹 → 保存改名 → 移动分组 → 搜索 → 打开 → 再编辑 → 删除分支。
- 锁定白棋 → 创建连续白棋研究分支 → 解除锁定 → 删除 → 放弃 → 重开。
- 在保存防抖尚未结束时快速切节点、切谱或关闭弹窗。
- 对同一按钮进行连续快速点击，确认不会产生重复记录、重复题目、重复下载或状态翻转两次。

## 自动化脚本要求

- 自动化应从真实 UI 入口操作，优先按 role、aria-label 和可见文字定位。
- 每个关键动作前后保存结构化快照，不只截图。
- 快照至少包括：documentId、currentId、depth、visibleStoneCount、nodeCount、branchCount、draftOperationCount、activeLargeId、localStorage 关键键和 IndexedDB 摘要。
- 监听 `console.error`、未捕获异常、请求失败和超过阈值的操作耗时。
- 每发现一个 Bug，先写能失败的最小回归；修复后将该回归保留在 `qa/` 或单元测试中。
- 自动化通过后仍做一轮手工探索，重点观察视觉、触感、信息层级和误操作风险。

## 缺陷优先级

- P0：数据丢失、棋谱损坏、错误覆盖、无法导入/打开、页面崩溃。
- P1：跳错节点、步数错乱、保存刷新不一致、删除范围错误、严重卡顿。
- P2：功能可用但状态、提示、布局或移动端操作明显不合理。
- P3：视觉细节、措辞、轻微间距和低频体验问题。

一次对话优先清零 P0/P1，然后尽可能多处理 P2/P3。若未修复，必须记录复现证据和原因，不能省略。

## 回报格式

GLM 的下一份回复应汇总整轮成果，而不是每修一个问题就单独结束：

```text
验收基线：分支 + 完整提交号
覆盖范围：执行了哪些测试矩阵
发现问题：P0/P1/P2/P3 各多少
批量修复：按功能域列出问题、文件和提交号
回归结果：命令、浏览器视口、真实文件和前后快照
性能数据：关键操作耗时和长任务
体验改进：发现并修正了哪些不好用的地方
遗留问题：复现步骤、风险和未修原因
```

没有执行完整测试矩阵时，不得写“未发现其他问题”；只能写“本轮已覆盖的范围内未发现”。

## 与 Codex 并行时的边界

GLM 可以在一次对话中修复很多问题，但仍只在 `glm/qa` 工作树操作。若 Codex 同时修改热点文件，可以先完成测试和定位，再把相关问题组成一份清晰报告；对于不会冲突的存储、格式、测试或独立组件问题，可以直接批量修复。不要进入 Codex 工作树，也不要覆盖 `codex/features` 分支。

收到本文件后，请不要只回复计划；直接开始第一轮广泛验收并持续推进，尽可能在一次对话中交付更多有效修复。
