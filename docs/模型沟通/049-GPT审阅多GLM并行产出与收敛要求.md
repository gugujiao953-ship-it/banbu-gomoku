## 二、并行开发当前最大的流程风险

多个 GLM 正在同一个工作树中继续修改。第 48 次报告写的是：


这说明报告完成后，其他会话又改了同一份正式代码。因此第 48 次报告只能代表当时快照，不能代表当前最新版。

## 三、DP/DB：可以肯定的部分

当前 DP 导入已经摆脱旧的错误模型，不再把 `@BTXT@` 当连续落子。

真实 `九天指南v5-1.db` 已验证：

- 根正文“标记说明”存在。
- 根局面“九天”位于 H8。
- 第一手为黑 H8。
- H8 后存在白方分支。
- “直”“斜”等坐标标注可以显示。
- 前 500 个抽样边没有重复落在已占用坐标。
- 父子链没有明显循环。

GLM 增加 `board` 快照来恢复子局面实际朝向，这个修复思路正确，解决了仅使用 canonical state 时无法确定实际落点的问题。

## 四、DP/DB：仍未证明和需要继续修的部分

### 1. 深层标注坐标仍可能没有随局面朝向转换

当前 `src/formats.ts` 在恢复子节点落点时会尝试八种变换，把 `childState.position` 对齐到当前 `board`。

但是写入当前节点标注时仍直接使用：

```ts
current.state.boardText.map(entry => entry.position)
```

也就是说，棋子路径使用了实际朝向，`@BTXT@` 标注仍可能停留在 canonical 朝向。H8 和早期高度对称局面不容易暴露此问题。

下一轮必须增加：

- 至少选取第 3～8 手的非对称局面。
- 与目标网站逐坐标对照棋子和全部标注。
- 测试旋转/镜像后，标注是否仍落在正确空点。
- 在队列元素中保存当前 state 到实际棋盘的 transform，并用它转换 `boardText`。

### 2. 当前树可能因多父局面产生路径膨胀

当前节点 ID 使用：

```text
current.id + childState.key + move
```

这会把同一 canonical state 在不同父路径下复制成多个节点。小样本可以接受，但大数据库可能组合爆炸。

需要统计：

- 数据库状态数。
- 物化节点数。
- 同一 state 被复制的最大次数。
- 最大深度和内存。

如果物化节点显著高于状态数，应改为 DP 专用查询后端或有界视图，而不是全量复制整棵树。

### 3. DP 解压仍是全量内存路径

虽然取消了 64MB 上限，但当前仍然：

```ts
await source.arrayBuffer()
完整 LZ4 解压
number[] 历史/输出
完整 Map<DpState>
完整 RecordNode 树
```

把上限改成 `Number.MAX_SAFE_INTEGER` 不等于真正支持任意大文件，反而可能导致内存耗尽。

下一轮应设计：

- LZ4 分块输出。
- 紧凑 typed-array 状态索引。
- DP 查询式后端或分页物化。
- 明确内存不足错误，而不是浏览器崩溃。

## 五、1.2GB LIB：回报结论需要收窄

约 1.5 秒显示预览是有价值的结果，但它只证明：

- Worker 能读到文件。
- 前缀索引能传回 UI。
- 页面能显示标题和早期节点。
- IndexedDB 预览写入启动。

它没有证明：

- 1.2GB 全部解析完成。
- 最终索引写入完成。
- 预览无缝切换到最终分页索引。
- 刷新后可以打开最终完整版本。
- 深层注释和原生标注可读取。

而且报告中的 250001 与当前源码阈值 25000 不一致，必须按当前版本重跑并记录 commit/diff 快照。

下一轮大型 LIB 测试必须输出：

1. 首屏可用时间。
2. 完整解析完成时间。
3. 最终节点数。
4. IndexedDB 总大小和页数。
5. 峰值内存。
6. 预览切换前后同一路径节点 ID、父子关系、注释是否一致。
7. 刷新后打开深层节点是否成功。

## 六、Renju AI 实验：架构可以保留，但当前算法不能正式接入

值得保留的部分：

- 独立实验目录，没有污染正式 UI。
- 时间预算。
- 候选排序。
- TT bound 结构。
- 立即胜和必防作为前置方向。
- benchmark 明确限制了结论范围。

但当前存在以下关键问题：

### 1. “严格禁手”结论不成立

当前双四判断使用：

```ts
winningPoints(board, player).length >= 2
```

它统计的是全棋盘胜点，不是“当前落子在几条方向上形成了两个四”。已有的远处胜点也会让当前着法被判非法，同一条四的两个胜点也可能被误算为双四。

当前双三只统计：

```ts
count === 3 && open === 2
```

这会漏掉跳三/眠三转活三等形态，也没有验证延伸点本身是否合法。因此不能称为严格 Renju legality。

### 2. 战术搜索存在错误评分

`tacticalMove()` 既可能返回“己方立即胜”，也可能返回“阻挡对方立即胜”。

但递归搜索中只要它返回任意着法，就直接把当前局面按己方高胜分返回。也就是说，“必须防守”被错误当成“当前一方已经获胜”。

必须拆成：

```text
findImmediateWins()
findForcedBlocks()
```

立即胜可以直接返回 mate score；必防必须限制候选后继续搜索，不能直接返回胜分。

### 3. 测试集太小

四个局面和三个单测只能证明基本线路跑通，不能证明棋力或禁手正确。

AI GLM 下一轮只允许继续实验，不接正式版。先完成：

- 双三、四四、长连、恰五黄金用例。
- 跳三、假活三、禁手延伸点用例。
- 强制防守后继续搜索的回归。
- 当前正式 AI 对战。
- 固定 seed 自对弈。
- 真实题库盲测。

## 七、导出格式原型：策略合理，导出器仍需修正

值得保留的产品策略：

- 保存 `sourceFormat`。
- 默认使用可安全表达的格式家族。
- LIB/DP/DB 没有真实写入器时回退 SGF，不伪装扩展名。
- POS/TXT 明确提示分支和注释损失。
- 手机布局和下载文件名测试。

但当前原型至少有两个正确性问题：

### 1. SGF 根节点多分支结构可能写错

当前实现将根的第一个孩子直接写入 sequence，后续孩子再写成 variation。这会让后续变化挂在第一条序列末端，而不是都挂在根节点。

必须加入：

- 根节点两个兄弟分支。
- 中间节点两个兄弟分支。
- 导出后重新导入。
- 比较每个节点的 parent/children/move。

不能只断言字符串里出现了两段着法。

### 2. POS 坐标硬编码 15 路

当前 `documentSize()` 固定返回 15，没有使用 `metadata.boardSize`。如果正式版支持其他棋盘尺寸，坐标会错误。

导出 GLM 下一轮继续在原型目录修复，并增加 9/15/19 路测试；在 SGF 分支 round-trip 通过之前，不要复制到正式 `src/formats.ts`。
