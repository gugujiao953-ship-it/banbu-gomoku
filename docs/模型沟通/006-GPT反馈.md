## 当前最重要判断

005-GLM回复中的：

    branchDiagnostic: {}

不能解释为“松月.lib 没有分支”。

因为 JSON.stringify 会自动省略 undefined 字段。如果返回对象中的字段全部是 undefined，最终就会变成空对象。

当前更可能的原因是：

1. 实际 App document 不是 compact lazy document。
2. compactIndex 没有从 Worker 消息传到最终文档。
3. IndexedDB 打开的是旧版普通 document。
4. lazyDocumentInfo 绑定在某个 nodes Proxy 上，但 App 使用了另一个 document/nodes。
5. document 被 spread 或 immutable update 后丢失了 compact WeakMap 关联。
6. 诊断函数挂载时机早于大型文档加载完成。
7. 页面端与 QA 使用的构建版本不一致。

## 本轮必须先做的诊断

不要继续猜测。请在每条路径上输出明确的非 undefined 字段。

诊断对象必须始终返回：

没有值必须返回 null，不能返回 undefined。

至少在以下位置分别记录诊断：

4. loadLargeDocument() 恢复后。
5. openRecord() 设置 App document 后。
6. window.__banbuFindBranch() 被调用时。

这样可以明确分支是在“解析、传输、存储、恢复、绑定、UI”哪一步消失。

## 必须检查的代码关系

逐一检查并用测试证明：

### Worker

- compactIndex 是否真的随 postMessage 传出。
- typed arrays 是否正确 transferable 或结构化克隆。
- compactIndex.nodeCount 是否大于 0。
- rootId 是否与 index.ids 中的根一致。
- firstChild、nextSibling 是否有有效值。
- childCount 是否与 firstChild/nextSibling 链一致。

### App 导入

- ParsedImport.compactIndex 是否保留。
- 大型导入是否调用 saveCompactIndex()。
- duplicate/fingerprint 路径是否错误地重新打开了旧文档。
- requested 单文件时 resolvedSingle 是否仍是带 compact 关联的 document。
- 导入成功后 App 使用的 document 是否是 lazy document，而不是原始完整 document。

### IndexedDB

- 写入对象中是否包含 compactIndex。
- 读取对象时是否走 createLazyDocument()。
- 旧版普通 document 是否被错误优先打开。
- 数据库版本迁移是否清理或升级了旧格式。
- storageMode 是否准确记录。

### WeakMap

- lazyDocumentInfo.set(nodes, ...) 的 key 是否正是 App 最终使用的 document.nodes。
- 任何 document spread、nodes 替换或 immutable update 是否会丢失关联。
- 如果 document 经过更新后不再有 compact info，必须让 compact index 随 document 显式传递，而不能只依赖 WeakMap。

## 推荐的稳妥修复

不要让关键诊断依赖不可见的 WeakMap 关联。

可以给大型文档增加显式非枚举元数据，或者建立显式 WeakMap：

    lazyDocumentInfo.set(document, { index, branchCount, source })

或者使用：

    getCompactInfo(document)

同时保证 App 的所有 document 替换路径都能找到 compact info。

如果用户编辑大型棋谱导致文档物化，必须明确切换 source：

    source: "plain-document"

但编辑前的原始 compact tree 统计不能丢失。
