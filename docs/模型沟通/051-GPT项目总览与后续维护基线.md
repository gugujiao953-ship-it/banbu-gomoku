## 2. 用户真正想要的产品

用户希望把成熟桌面五子棋工具的核心体验迁移到手机和网页，而不是做一个只能在空棋盘上落子的演示：

1. 打开普通棋谱、RenLib 开局库和 DP/DB 局面数据库。
2. 保留主线、分支、父子关系、兄弟变化、节点注释和棋盘标注。
3. 在任意历史节点继续编辑，能从旧节点创建新分支，而不是只能走回最新主线。
4. 支持做题、题集管理、人机对弈和“思考当前局面”。
5. 保存、导出、导入和棋谱库行为要让普通用户看得懂；文件路径、来源格式和格式损失要有明确说明。
6. 大型棋谱可以较快打开，不能因为把整个千万节点树塞进 React 状态而卡死。
7. AI 必须本地运行，不把棋局上传到未知网站；强度需要用真实高级题库测试，而不是只看它会不会在空盘落子。

核心交互原则是“棋盘优先、底部工具坞、触控友好”：

- 空交叉点轻触是落子。
- 低频功能放入底部面板或抽屉。
- 标注、注释、分支、元数据不能迫使用户离开当前局面。
- 主要操作尽量有约 44px 触控区域。
- 已有棋子的点击行为已经针对误触和回看体验调整；如果后续修改，必须以当前 App.tsx 和浏览器测试为准，不要直接照搬旧文档描述。

## 4. 技术架构和数据流

### 4.1 总体技术选型

- React、TypeScript、Vite：网页界面和共享业务逻辑。
- PWA / Workbox：离线网页。
- Capacitor 8：Android 壳，不复制棋谱业务逻辑。
- Web Worker：AI、VCF、普通大文件导入、DP 查询和 RenLib Web 核心。
- localStorage：普通小型棋谱和轻量 UI 状态。
- IndexedDB：大型棋谱、compact 分页索引、草稿和目录句柄。
- SVG 棋盘：当前 UI 的棋盘绘制；大型资料使用有限投影，不能随意改成全量节点渲染。

### 4.2 普通棋谱路径

    文件选择
      -> 格式识别与大小判断
      -> SGF / JSON / POS 等专用解析器
      -> GameDocument + RecordNode 变化树
      -> 普通存储或大型 compact 存储
      -> App 当前节点 / 路径 / 分支窗口
      -> 棋盘、注释、标注、搜索、导出

### 4.3 .lib 路径

    .lib
      -> RenLibWebViewSession
      -> RenLibWebSession
      -> RenjuLib_worker.js + RenLib WASM/JS
      -> 当前局面、路径、直接子分支、注释查询
      -> LibraryViewSession 有界投影
      -> 复用现有棋盘和面板 UI

正式 .lib 入口不是旧的 eager importRenLibLegacy。src/renlib-web/ 中保留了从公开网页实现移植的核心文件，生产路径通过 Worker 查询；旧解析器只用于对照和兼容测试。

### 4.4 .db/.dp 路径

    .db / .dp
      -> dp-database.worker.ts
      -> LZ4 Frame 解码、数据库记录索引
      -> openDpDatabaseIndex / queryDpPosition
      -> DpViewSession
      -> 当前局面和下一层分支投影
      -> 现有棋盘 / 注释 / 分支 UI

这类文件不是普通着法文本，也不是 SQLite。数据库记录更接近“局面键 -> 当前局面注释 / 局面标注 / 子局面”。历史上把 @BTXT@ 内容按顺序当作落子，造成后半盘坐标、分支和注释全错；这已经通过局面查询模型和真实文件回归修复。

### 4.5 AI 路径

    App.tsx
      -> 人机 / 做题 / 思考
      -> Rapfi 本地 WASM Worker
         或 puzzle-ai.worker.ts
      -> VCF 搜索与 verifyVcfProof
         或 renju-ai/engine.ts 迭代加深搜索
      -> 结果实例校验
      -> 回显推荐点 / 自动落子

停止、切题、重启和退出时必须终止旧 Worker，不能让旧结果写回新棋盘。

## 5. 核心数据模型

核心文件是 src/types.ts、src/game.ts、src/formats.ts：

- GameDocument：棋谱 ID、版本、根节点、节点表、元数据、时间和保存游标。
- RecordNode：id、parentId、children、move、comment、marks、preferredChildId、boardText、evaluation 等。
- setup：SGF 的 AB/AW/AE/PL，改变局面但不伪造普通着法。
- passPlayer：SGF B[] / W[]，计轮次但不落子。
- anchor：RenLib 非落子节点携带局面文字或注释锚点。
- renLibAnnotations、renLibFlags、renLibExtendedFlags：保留原生字段，未确认的语义不能擅自翻译成用户标注。
- CompactRenLibIndex：parent、firstChild、nextSibling、childCount、preferredChild、moveCode、文本引用和标注引用等 typed array。

必须区分以下概念：

1. 用户编辑的棋盘形状标注。
2. 节点的文字和结构化评价。
3. RenLib 原生标注或原始 flag。
4. 非落子节点的文字锚点。
5. DP/DB 局面记录本身的候选子局面。

最危险的错误是把第 3、4、5 类伪造成普通棋子、伪造注释，或覆盖第 1 类用户标注。

### 阶段三：分支、编辑和草稿反复修复

用户多次反馈：回到前一步后无法在别的位置继续；点分支外的位置没有反应；删除后撤销棋子失去可编辑性；点击已有棋子会误跳到历史局面；保存按钮不清楚保存到哪里。

这暴露出的问题不是一个按钮问题，而是“当前游标、基线文档、草稿投影、分支目标”没有统一。后续加入和修正了：

- 从历史节点明确创建变化。
- 草稿投影和连续多步编辑。
- 删除子树的后代闭包。
- 撤销、重做、放弃和保存草稿。
- 普通谱与大型谱的存储隔离。
- 按文档 ID 隔离草稿，避免串谱。
- 离开、导入、新开人机前的未保存草稿高优先级拦截。
- 保存大型谱时提交为派生版本，不破坏原始定式库。

旧报告曾多次把“有操作日志”误判成“草稿已保存”。独立复验发现过真实数据丢失链：草稿可见但导出仍使用 committed baseline、保存后回到原始棋谱、派生版本 ID 不独立、切谱时草稿串谱。后续才形成现在的 overlay / derived version 方案。未来模型不能只测 toast 或按钮，要检查刷新、存储和导出内容。

### 阶段四：大型 LIB 和大文件性能

真实样本包括：

- D:\五子棋\定式谱\雨.lib，约 4.24MB。
- D:\五子棋\定式谱\松月.lib，约 131MB。
- D:\五子棋\定式谱\斜月.lib，约 1.185GB。

最初的完整对象树会造成内存、React 重渲染、localStorage 限制和手机卡顿。曾经出现“前两手正常，后面乱或卡”“什么都不点也会空闲卡顿”的反馈。改造方向：

- 8MB 以上或大节点数据转 Worker。
- compact typed-array 关系索引。
- IndexedDB 分块。
- 当前路径 + 有限分支窗口。
- 旧异步结果版本隔离。
- .lib 生产入口改用网页 RenLib WASM / JS 核心，动态查询当前局面。

历史报告中有“首批预览 25,001/250,001 节点”的不同阈值，也有只证明预览、没有证明完整索引的报告。后来 src/renlib-web/README.md 记录了一次 1.185GB 文件约 65.659 秒到达完成信号并继续可查询。以后测试必须标明 commit、阈值、文件、完整完成信号、峰值内存和深层查询结果，不能把首屏预览冒充全量导入。

### 阶段五：DP/DB 根因修复

用户指出九天数据库“开局一两步对，后面越来越乱”。真正根因是：

1. DP/DB 局面键按八种对称变换 canonicalize。
2. 父状态和子状态可能选择不同 canonical 方向。
3. 旧代码直接把子状态的 canonical 坐标当实际棋谱坐标。
4. 深层路径因此会重复落到已占用点，分支和颜色也会错。

真实失败曾在第 9 手出现重复坐标。修复后，队列状态携带当前真实棋盘，子状态尝试八种变换，只接受“与真实父盘恰好一个合法差异”的落点。真实九天文件在深度 20、500+ 条边范围内通过无重复坐标、无错误轮次和无循环路径检查。

旧的 DP 整树反推代码已隔离到 src/legacy-dp.ts，正式 .db/.dp UI 使用 DpViewSession 和查询 Worker。不要为了兼容旧测试把旧整树路径重新接回正式入口。

- 五手两打。
- 五手 N 打。
- 塔拉山口-10。

## 8. 文件格式真实能力

### 导入

- SGF / FGF：SGF FF[4] 游戏树、设置局面、过手、多个顶层棋谱、注释、节点名、常用标记、评价和基础元数据。
- REN / RENJS / WZQ：内容确实是 SGF 语法时按 SGF 读取，不能只凭扩展名保证兼容。
- JSON / RENJU：本项目完整 GameDocument，也接受明确声明 coordinateBase 的落子列表；题库 JSON 是单独适配器。
- POS / TXT：纯坐标序列，例如 H8 I8 H9，不把它包装成拥有分支和注释的标准。
- DP / DB：支持已确认的 LZ4 + 私有局面数据库结构；不保证所有同扩展名私有变体。
- LIB：使用 RenLib Web 动态核心读取主线、分支、文字和常见原生字段，扩展字段保守处理。

### 导出

- SGF：正式重编码格式，适合与 RenLib 和其他棋谱工具交换，能表达变化树、注释、标记和基础评价。
- RENJU JSON：正式完整跨端格式，保存本项目变化树和编辑字段。
- 已打开且原始字节仍被保留的 LIB / DP / DB：可做原文件直出；这不是把编辑后的投影重新写回对应私有二进制。
- POS / TXT：如果后续提供导出，只能是明确提示有损的主线坐标文本，不能声称保留全部棋谱信息。
- 任意“LIB 转成 LIB”“DP 生成 DB”等尚未实现的转换不得伪造扩展名。无法无损表达时应回退到 SGF 或 JSON，并说明损失。

sourceFormat、sourceFileName 用于决定导出按钮策略。后续如果修改导出 UI，必须把“原始直出”和“转换导出”分开描述。

## 9. AI、规则和 benchmark 现状

### 9.1 本地运行

public/rapfi/rapfi-worker.js 明确只加载随包的 fallback 资源，不访问 gomocalc.com。过去的实现会产生一次远程数据请求和超时日志；那不是把棋局上传到云端计算，但会访问网络、体验不稳定，也不符合用户的本地优先要求，已经移除。

### 9.2 正式 Worker 行为

src/puzzle-ai.worker.ts 的策略是：

1. 先用 VCF 找强制胜。
2. 用 verifyVcfProof 独立校验，校验失败不把结果暴露为已证明。
3. 没找到验证通过的 VCF 时，走增强 alpha-beta。
4. 棋谱“思考”使用更大的时间和节点预算。
5. 做题 / 人机和思考都由实例和终止机制保护。

### 9.3 15 步高级题要求

用户最终明确的强度标准是：

> 对题库中的“三手胜高级题”，每一道题最多给 AI 15 步容错；不是只抽 3 道题。应多测、最好默认跑完整题集，15 步以内找到合法且正确的胜法才算该题通过。

当前代码情况必须注意：

- src/ai-benchmark.ts 的 maxSteps 默认是 15，并把 15 个半步转换为最多 8 个攻击手数，结果还要经过完整 VCF proof 验证。
- scripts/benchmark-rapfi.mjs 默认 AI_PUZZLE_PLIES=15，默认读取完整 三手胜4-高级题.json，并在未全通过时返回失败。
- scripts/benchmark-ai.mjs 当前仍显式传入 maxSteps: 10，这是旧基准残留，与用户最终 15 步要求不一致，后续应先修正脚本再把结果当作正式强度结论。
- 当前单测只是一个合成高级题和若干固定规则用例；它不等于整套真实高级题通过。
- 没有经过完整题集、固定时间、固定引擎、失败题列表和可复现环境记录之前，不得写“AI 已达到合格棋力”。

### 9.4 规则限制

黑方长连、四四、三三在当前规则路径中会被列为禁手；精确五连可以获胜。研究模式和普通人机模式的阻止策略要分开看，后续修改前先检查 evaluateRenjuMove 的调用方，不要只改棋盘颜色。
