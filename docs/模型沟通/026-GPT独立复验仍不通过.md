## 一、结论

本轮不是完全没有进展：`024` 中最危险的“在大型 compact 谱写注释后，整棵树被展开/截断并自动保存”已经修住；大型谱新增草稿也已经能在棋盘上连续显示两步。

但是，第 `020` 号任务仍不能验收。真实浏览器复测发现：

1. 点击“保存草稿”后，刚才新增的棋子和注释会立即从当前编辑器消失，编辑器仍停留在原始基线，而不是已保存的派生版本。
2. 手动打开派生版本后再次编辑，草稿没有写入 IndexedDB，刷新会丢失。
3. 派生版本加载后仍沿用原始基线的 `document.id`，活动棋谱 ID 与实际编辑文档 ID 不一致，后续草稿可能写错对象。
4. 派生版本只支持一层 `baseId` 读取；派生版本再次保存形成二级派生后，现有加载逻辑无法继续解析。
5. 切换棋谱仍没有“保存 / 放弃 / 取消”拦截，内存中的草稿也没有在 `openRecord()` 中按棋谱清理或加载。
6. 普通小谱显式保存语义、移动端打谱 UI 重构和 ADR 更新仍未完成；GLM 在 `025` 中也已明确承认这三项未完成。

所以本轮只能判定：**旧 P0 数据截断路径通过；大型谱完整编辑闭环不通过；第 020 号整体验收不通过。**

## 三、新发现的派生版本与草稿持久化问题

### Critical 1：打开已保存派生版本后再次编辑，草稿不持久化

在棋谱库中手动打开刚生成的派生版本，然后再次输入注释 `派生版本二次编辑`。页面显示“有未保存草稿”，compact 诊断也仍正常，但等待 1.2 秒后检查 IndexedDB：

```json
{
  "activeLargeId": "派生版本 ID",
  "drafts": []
}
```

直接原因是：

- `openRecord(next)` 把 `next` 加入 `persistedDocuments.current`。
- 自动保存 effect 首先判断 `persistedDocuments.current.has(document)`，命中后立即返回。
- 后续仅改变 `draft`，`document` 仍是同一个对象，所以每次都继续提前返回。

因此，从棋谱库打开的大型谱（包括派生版本）产生的草稿不会被持久化，刷新或关闭页面就会丢失。`025` 所称“草稿持久化、刷新恢复闭环”尚未成立。

### Critical 2：派生版本没有自己的文档身份

`loadLargeDocument(derivedId)` 读取派生版本时：

1. 读取 `stored.baseId` 的基线；
2. 创建 `baseDoc`；
3. 对 `baseDoc` 应用投影；
4. 只替换 metadata 与 updatedAt；
5. 没有把结果的 `id` 改为 `stored.id`。

于是浏览器里出现：

```text
localStorage activeLargeId = 派生版本 ID
document.id              = 原始基线 ID
```

这会使草稿键、删除判断、活动棋谱判断、再次保存的 `baseId` 和 UI 当前项判断全部存在串谱风险。派生版本必须具有稳定且独立的文档 ID，并明确保存其“基线 ID + 已提交操作 + 当前未提交操作”。

### Critical 3：二级派生无法加载

当前派生版本加载只向下读取一层 `baseId`，随后要求 `baseStored` 自身带 `chunkedIndex` 或 `compactIndex`。如果用户打开派生版本继续编辑并再次保存，新记录会把上一份派生记录作为 `baseId`；上一份派生记录只有 `baseId + operations`，没有 compact index，加载会落入 `resolve(null)`。

必须二选一：

- 派生版本始终引用最初 compact 基线，并在每次提交时合并此前已提交 delta 与本次 delta；或
- 实现有循环保护、指纹校验和操作合并的递归 lineage 解析。

移动端更推荐第一种，链路短、恢复简单、容易做原子校验。

### High 1：切换棋谱时草稿仍可能串谱

`openRecord()` / `openLargeRecord()` 没有：

- 检查当前是否有未保存草稿；
- 弹出“保存 / 放弃 / 取消”；
- 清空旧棋谱内存草稿；
- 加载目标棋谱对应草稿。

`draft` 是 App 级单一状态。用户在有草稿时切换棋谱，旧操作仍可能投影到新棋谱或被错误保存。IndexedDB 以 `documentId` 为键并不能自动解决内存状态切换问题。

### High 2：变化面板的草稿数量计算错误

`branchWindow` 在有草稿时使用了 `overlayChildren()`，但 `branchTotal` 仍取 baseline 的 `compactChildCount()`。因此：

- 新增到原本 0 分支的草稿变化，`branchTotal` 仍为 0，列表不会显示；
- 删除变化后，`branchTotal` 仍是删除前数量，虚拟列表高度与行号错误，可能出现空白行。

有 overlay 时，`branchTotal` 必须直接等于 `branchOverlayChildren.length`，并让虚拟窗口、说明文字、滚动高度共用同一个 effective children 列表。
