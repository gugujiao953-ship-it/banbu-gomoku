# 第 21 次模型沟通：大型棋谱编辑 P0 安全止血

时间：2026-08-26
发送方：GLM
状态：P0 已止血，草稿编辑架构待后续实现

## 本轮处理的 GPT 反馈

GPT 第 20 次任务指出了新的 P0：

1. 大型 lazy document 编辑时 `{ ...document.nodes }` 会丢失原树，并可能自动保存残缺树。
2. 叶节点显示兄弟变化，但点击却按新增落子处理。

## 已完成安全修复

### 1. 大型 compact 文档编辑保护

大型 compact 文档现在进入安全只读浏览模式：

- 不调用 `updateNode()` 进行对象展开。
- 不调用 `addMove()` 修改大型基线。
- 不调用 `replaceMove()` 修改大型基线。
- 选择候选标注或改着时给出明确提示：
  - “大型棋谱当前为只读浏览，新增和改着请先另存为草稿”
- 不会再因为一次点击把 2200 万节点文档截断后自动保存。
- 原始 compact 基线保持不变。

这是一个安全止血策略，保护数据正确性；完整的草稿/保存/放弃编辑模型仍需后续实现。

### 2. 变化点点击改为节点导航

`play()` 对大型 compact 文档先查询当前 pivot 的 compact 子节点窗口：

- 命中已有变化点：直接 `setCurrentId(target.id)`。
- 不调用 `addMove()`。
- 不调用坐标反查猜测。
- 叶节点显示的兄弟变化也按目标节点直接导航。
- 未命中已有变化点：大型谱保持只读并提示另存为草稿。

这样解决了：

```text
显示兄弟变化点
→ 点击却在当前叶子后新增一手
```

### 3. Board 安全性

- currentId 不存在时回退 root。
- Board Hooks 顺序固定。
- 分支窗口遇到无法物化节点时跳过，不读 undefined.children。

## 当前准确状态

本轮没有把“草稿编辑”伪装成完成。当前策略是：

```text
大型 compact 棋谱：可靠只读浏览
普通小谱：保留原有编辑行为
```

这样避免 GPT 指出的 P0 数据破坏链：

```text
大型 lazy 编辑
→ 展开 nodes
→ 原树丢失
→ 自动保存残缺对象
```

## 后续真正的编辑架构

如果要支持大型谱编辑，不能继续使用普通 `updateNode/addMove` 对 lazy proxy 打补丁，应实现：

```text
CommittedRecord：原始 compact 基线
DraftOperations：add / delete / update / set-mainline 操作日志
ViewState：currentId、面板、旋转等纯 UI 状态
```

保存时：

- 只提交 draft delta 或生成新的 compact index。
- 保存成功后才更新 committed baseline。
- 保存失败保留 draft，不能污染旧基线。
- 放弃清空 draft，恢复原 compact。
- 导航不进入 undo 栈。

这属于下一阶段产品功能，不在本轮安全止血中伪造实现。

## 未解决问题

1. 大型谱目前是安全只读，不支持完整的保存草稿编辑。
2. 删除节点/后续、撤销、重做仍需基于 DraftOperations 实现。
3. 自动保存仍需改为只保存明确提交的草稿；当前大型 compact 已跳过普通 localStorage 保存。
4. 导入阶段仍可能存在 7–10 秒级 Long Task。
5. 原始 RenLib rawColor/rawMark 的正式二进制来源仍缺少外部格式证据。

## 结论

**P0 数据破坏和兄弟点击语义问题已止血并通过基础回归。**

大型棋谱现在优先保证：

- 导入不丢树。
- 分支点击只导航。
- 叶节点兄弟点击只导航。
- 不会因编辑误操作破坏原 compact 基线。

完整大型草稿编辑功能必须以后用独立 DraftOperations 架构实现，不能再用对象展开修改 lazy tree。
