## 三、注释常驻是否是主要卡顿源

检查了 `App.tsx` 的注释常驻路径：

```text
hasNativeAnnotation(current)
annotationLines(current)
commentExpanded
comment-review
```

这些逻辑只针对当前节点的注释/原生标注数组，不会扫描整棵大谱；常驻按钮也只读取当前节点。因此没有证据表明“注释常驻本身”造成了大型谱空闲期间的全树重算。

同时验证真实 `雨.lib`：

```text
普通 comment：50 个
boardText：693,585 个
```

两类文本均在 compact `textRefs/texts` 中保存，注释常驻只是读取当前节点，不会遍历 693,585 条文本。

## 四、真正发现的高风险卡顿/崩溃链

### 1. 预览消息复制与 Worker 继续扩展同一索引

旧路径：

```text
Worker 解析到预览阈值
  → postMessage(compactIndex)
  → 主线程结构化复制 25 万节点 typed arrays
  → Worker 继续扩展原 builder
  → 最终 toIndex 再生成完整 typed arrays
  → IndexedDB 分块写入
```

深测表现：

```text
等待 finalOnly 期间 Page crashed
雨.lib：page.waitForTimeout: Page crashed
松月.lib：Target crashed
```

这说明“打开后什么也不做卡一下/后续变坏”的主要嫌疑是索引复制和完整索引阶段的内存峰值，不是注释按钮的单节点读取。

### 2. 预览与完整结果重复写入/重复打开

旧路径还存在：

```text
preview 先由主线程处理
finalOnly 到达后又调用 openLargeRecord(summary)
```

这会在同一导入过程中重复创建/关闭大型分页句柄和页面投影，增加后台竞争与重建开销。

## 五、本轮修复

### A. 预览不再把 buffer 所有权转移给主线程

`src/record-import.worker.ts`：

- 预览消息不再调用 `transferIndex(preview.compactIndex)`。
- Worker 继续拥有实时构建器的 typed-array 页面。
- 预览走结构化复制，只发送有限窗口。
- 完整索引仍在 Worker 内写入存储。

### B. 预览不再被 `handleFiles` 当作正式索引再次写入

`src/App.tsx`：

- `prepared?.preview` 只作为临时 UI 结果。
- 不再用预览 compact index 调用 `saveCompactIndex()`。
- 完整索引只由 Worker finalOnly 路径持久化。

### C. finalOnly 不再递归重新打开同一记录

`src/App.tsx`：

- finalOnly 只更新摘要和导入状态。
- 不再在当前活动记录已经显示预览时递归 `openLargeRecord()`。
- 避免重复分页句柄和重复 UI 投影重建。
- 完整索引完成后仅写入 active 标识和 `compact-complete` 状态。

### D. 预览阈值降低为 5,000

`src/formats.ts`：

- 预览窗口从 250,000 降为 5,000 节点。
- 目标是避免在 Worker 继续增长完整索引时产生大块结构化复制。
- 首屏仍能快速显示标题、早期局面和少量分支。
