# 第 12 次模型沟通：分支选点显示失真与移动端可读性反馈

时间：2026-08-25
发送方：GPT
状态：待处理

## 一、用户实际反馈

用户在网页版中实际浏览大型棋谱后确认：

1. 网页整体速度主观上已经可以接受；如果还能进一步加快更好，但当前最明显的问题是棋盘分支选点显示失真。
2. 几乎每个有分支的局面，前 26 个分支点都会依次显示字母；26 个字母用完后，其余分支点才变成没有字母的空点。
3. 用户怀疑原棋谱中的这些点本来可能是不同文字，或黑、白、蓝等不同颜色的选点，不应由网页统一改成字母。
4. 当前每个分支点都被圆形框住，字母很小，手机上不容易看清。
5. 如果原谱本来就是字母或其他文字，建议去掉圆框，直接清晰显示原始内容。
6. 总原则：原棋谱怎么显示，网页尽量就怎么显示；网页不能自行给所有分支编造字母。

## 二、已确认根因

用户的观察准确，不是 RenLib 文件本身给每个分支都写了 A–Z，而是网页渲染代码自行生成的。

`src/App.tsx` 当前逻辑：

```tsx
{variationNodes.map((node, index) => {
  ...
  <circle ... className="renlib-variation-dot" />
  ...
  {index < 26 && (
    <text ...>{String.fromCharCode(65 + index)}</text>
  )}
})}
```

这段代码造成：

- 第 1～26 个分支被强制显示为 `A–Z`。
- 第 27 个及以后不再渲染文字，所以只剩空点。
- 字母只代表数组顺序，不是原棋谱数据。
- 每个变化无条件先画 `circle`，因此所有文字都被圆点包住。
- CSS 将字母固定为约 7px 的 SVG 字号，手机上过小。

当前解析与 compact 数据结构只保留：

- `comment`
- `boardText`
- `evaluation`
- `renLibMark: boolean`

没有完整保留原谱显示所需的：

- `rawText`
- `rawMark`
- `rawColor` / `status`
- 原始显示类型
- 语义分类
- 是否应显示圆点、文字或颜色点

所以目前不是单纯改 CSS 就能完全修好。必须同时修正解析数据模型和 UI 渲染规则。

## 三、必须修改的显示原则

### 1. 禁止自动给棋盘分支生成 A–Z

- 删除棋盘变化点上的 `String.fromCharCode(65 + index)` 自动编号。
- 分支没有原始文字时，只显示原谱对应的点样式；如果原谱也没有标记，显示简洁的中性候选点。
- 如果产品仍需要序号，只能放在“变化分支”列表中，不要伪装成原谱棋盘标记。

### 2. 原谱文字直接显示，不统一套圆框

- 原谱为字母、汉字或短文本：直接显示文字，不画底层圆点或圆框。
- 1～2 个字符使用清晰大字号；3～4 个字符允许略微缩小，但不能缩成当前难以辨认的 7px。
- 建议 SVG 字号约 11～13，使用适度 `paint-order: stroke` 浅色描边保证木纹棋盘上的对比度。
- 文字本身 `pointer-events: none`，仍保留独立透明点击热区，避免视觉元素变小导致难点按。

### 3. 原谱颜色点按原样区分

- 黑点：黑色实心点或原软件等价样式。
- 白点：白色实心点并加深色细边，确保浅色棋盘上可见。
- 蓝点：蓝色特殊点，不转换成字母。
- 未知颜色或类型：保留 raw 值，并用中性样式显示，不能自动解释成 A、B、C。

### 4. a / c / ccc 使用已约定语义

- `a`：好点、胜点、推荐变化。
- `c`：败点、坏点。
- `ccc`：按 c 类败点处理，不在棋盘上重复显示普通 `ccc` 字符串。
- 数据层仍须保存原始文本，显示层使用 `semantic` 和 `displayKind` 决定样式。

### 5. 数据结构必须补全

建议为 RenLib 节点或变化显示信息增加等价字段：

```ts
interface RenLibDisplayMark {
  rawText?: string;
  rawMark?: number | string;
  rawColor?: string | number;
  semantic: "good" | "bad" | "special" | "unknown";
  displayKind: "text" | "black-dot" | "white-dot" | "blue-dot" | "neutral-dot";
  displayText?: string;
}
```

字段名可以调整，但必须同时保留 raw 数据和显示语义，不能再压缩为单个 `renLibMark: boolean`。

## 四、移动端视觉验收标准

1. 任意有分支的局面，不再自动出现连续 A–Z。
2. 超过 26 个分支时，不再出现“前 26 个有字母、后面全空白”的断层。
3. 原谱文字显示为原文字；原谱无文字时不编造文字。
4. 原谱文字不套统一圆框，手机 360px 宽度下肉眼可读。
5. 黑点、白点、蓝点视觉上明显可区分。
6. 白点在木纹背景上有足够边界对比度。
7. 点击热区仍至少约 34～44 CSS px，不因去掉圆框而变得难点。
8. 已经落子的棋子位置不叠加后续变化文字或颜色点。
9. 旋转、镜像、显示手数开关后标记仍在正确坐标。
10. 同一真实 .lib 与爱五子棋/原查看器截图逐局面对照，记录每个标记的原谱显示、网页显示和 raw 字段。

## 五、必须增加的测试

- 原谱无标签分支：不得自动生成 A–Z。
- 原谱文字 `a`：保存 rawText，显示推荐语义。
- 原谱文字 `c`、`ccc`：保存 rawText，显示败点语义，不显示大量普通 ccc。
- 原谱普通字母或汉字：直接显示原文且无圆框。
- 黑点、白点、蓝点：分别命中对应 CSS/displayKind。
- 27 个以上分支：第 1～全部分支都按原谱数据显示，不以 26 为分界。
- 已落子位置：不显示后续分支标记。
- 360×800、412×915 截图回归：文字清晰、无遮挡、无棋盘溢出。

## 六、优先级与结论

优先级：**P1，高于纯粹继续压缩几毫秒导航耗时。**

当前速度在用户实际体验中“倒是还行”，因此性能优化可以继续，但不要为了追求 compact 而丢失原始显示字段。下一阶段应先修复：

1. 大型谱分支点击崩溃。
2. 分支选点 A–Z 伪标签。
3. 原谱文字/黑白蓝点显示保真。
4. 手机字号与去圆框可读性。
5. 在不回退现有大谱速度的前提下继续优化 Long Task。

当前棋盘分支显示不能视为与原棋谱兼容；它只证明“分支坐标存在”，尚未正确复现“分支如何显示”。
