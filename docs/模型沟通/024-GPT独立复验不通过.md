路径：

```text

→ 定位第一个真实分支节点
→ 点击“记录”
→ 点击“注释”
→ 输入“P0复验”并完成
→ 等待 1.8 秒
```

编辑前：

```json
{
  "hasCompact": true,
  "nodeCount": 694910,
  "branchCount": 131393,
  "current": "第 1 手 H8"

```

编辑后：

```json
{
  "hasCompact": false,
  "nodeCount": null,
  "branchCount": null,
  "status": "0 / 0 手 · 1 处分支",
  "variations": 0,
  "header": "已保存"

```

浏览器无 console error，但数据模型已经被截断。这恰恰说明不能只以“页面没崩、consoleErrors=[]”作为大型谱正确性的标准。

根因仍是：

- `src/App.tsx` 的注释输入直接执行 `setDocument(updateNode(document, currentId, ...))`。
- 局面文字、着法评价、清除评价也直接调用 `updateNode()`。
- 候选标记、批量标记同样存在直接 `updateNode()` 路径。
- `updateNode()` 仍使用 `{ ...document.nodes }`。
- 大型 lazy `nodes` Proxy 在大于 100,000 节点时不允许全量 `ownKeys()`。
- 新文档丢失 compact 绑定后，又被现有自动保存 effect 当作普通大型文档保存。

所以 GLM 第 23 号回复中的“P0 数据破坏链已关闭”与真实结果不符。

## 三、分级代码审查结果

### Critical 1：大型谱注释/局面文字/评价仍能截断并保存棋谱

位置：`src/App.tsx` 的 `sheet === "comment"`、`sheet === "boardText"`、评价按钮、候选标记；`src/game.ts` 的 `updateNode()`。

必须统一经过 `recordDraft()` 或一层禁止绕过的编辑命令入口。不能靠在 `play()` 顶部判断 compact，因为这些编辑入口根本不经过 `play()`。

验收测试必须真实操作上述每一个 UI 入口，并在操作前后检查：

```text
compactNodeCount
compactBranchCount
rootId
root first child
当前节点 parentId
IndexedDB committed fingerprint
```

### Critical 2：“保存草稿 / 使用导出保存”会丢草稿

当前大型谱点击保存只提示：

```text
大型谱草稿已记录，请使用导出保存，避免改写原始定式库
```

但 `exportSgf(document)` 和 `exportJson(document)` 接收的仍是 committed `document`，没有应用 `draftOverlay`。因此用户按提示导出，导出的仍是原谱，草稿不会进入文件。

这不是可接受的“安全边界”，而是明确的数据丢失交互。完整 delta 提交尚未实现时，应禁用并明确标注“本版本大型谱不可编辑”，不能提供一个看似可用但无法保存的草稿流程。

### High 1：草稿 overlay 没有形成可连续编辑的棋盘

实测在 root 的 A15 新增大型草稿后：

- 顶部出现“有未保存草稿”。
- 当前手数仍是第 0 手。
- 草稿棋子不显示。
- currentId 不进入新草稿节点。
- 再点同一位置仍会继续记录另一条 `add-move`。

代码原因：

- `recordDraft(add-move)` 后没有切换 `currentId` 到 draft node。
- `boardAt()`、`pathToNode()`、`depthOf()`、`nextPlayerAt()` 都只读取 committed document。
- `Board.variationNodes` 的 `useMemo` 依赖缺少 `draftOverlay`；当前节点对象引用未变化时，草稿变化点也不会重新计算。
- compact `play()` 只在 committed compact 子节点中查询 target，无法导航到 draft node。

所以目前不能称为“大型编辑进入草稿态”，只能称为“记录了一条不可完成、不可保存的操作日志”。

### High 2：删除草稿在变化面板中不一致且不可保存

- `overlay.deleted` 只被 Board 的 overlay helper 部分读取。
- 变化面板的 `branchTotal`、`branchWindow`、行节点和预览仍直接读取 compact index / committed document。
- 删除提示写“点击保存后提交”，但大型保存根本不提交。
- 没有删除确认、预计删除数量和原子提交。

因此该入口的文案与实际能力不符。

### High 3：普通小谱仍违背“明确保存后才生效”

第 020 号任务要求所有棋谱采用：

```text
编辑 → 未保存草稿 → 用户确认保存 → committed 更新
```

当前普通小谱仍然：

- `addMove/updateNode/deleteVariation` 直接修改 document。
- 约 450ms 后自动写 localStorage。
- 删除变化无确认且立即生效。
- 在变化列表中浏览某变化仍会顺便修改 `preferredChildId`。

GLM 只给 compact 大谱加了一套半成品日志，没有实现统一产品语义。

### High 4：草稿状态没有按棋谱隔离

当前只有一个全局 `draft` state。检索当前源码，`newRecord()`、`openRecord()`、`openLargeRecord()`、导入完成和模式切换均没有可靠的“保存 / 放弃 / 取消”离开门禁，也没有按 `document.id` 保存草稿。

结果可能是：打开另一份棋谱后仍显示上一份棋谱的“未保存草稿”，旧操作引用旧 nodeId，形成幽灵状态或错误提交。

### Medium 1：移动端 UI 重构尚未发生

当前初始页真实可见按钮仍是：

```text
行棋 / 研究 / 记录 / 视图
起点 / 上一手 / 下一手 / 终点 / 变化
```

这与用户要求和第 020 号方案相比基本没有改变。当前 `mobile-visual` 只能证明无横向溢出，不代表信息架构、操作效率和棋手工作流已经完成。

### Medium 2：ADR 与最新用户决策冲突

`docs/adr/0002-large-record-storage.md` 仍把普通/大型棋谱自动保存作为架构决策；第 020 号用户任务明确改为手动提交草稿。ADR 仍是 `proposed`，且已与最新产品语义冲突。

GLM 在继续实现前应新增或更新 ADR，明确：

```text
committed baseline
draft overlay
explicit commit
transaction rollback
normal / compact 统一编辑语义
```
