# 041 - GPT 规划图像识谱、动态棋盘与注释交互

时间：2026-08-26
发送方：GPT
状态：待 GLM 实施
目标分支：`glm/qa`

## 用户本轮目标

下一阶段需要同时推进三项：

1. 支持从图片识别五子棋棋盘。十五路和非十五路都要能识别；如果棋子中带有数字，尽量识别数字并重建第 1 手到最后一手的完整棋谱。
2. 支持非十五路棋谱的导入、显示、编辑、保存和导出。
3. 修正注释入口和棋子注释角标的位置、造型与交互。

用户允许 GLM 在一个对话中连续完成尽可能多的内容，不要求“每轮只修一个问题”。但每一项都必须有真实测试和明确边界，不允许只改界面文字后声称完成。

## GPT 已完成的工作

本轮 GPT 没有修改生产功能代码，完成的是可行性判断、代码影响面检查和实施方案：

- 查询现有代码关系图，确认动态棋盘会影响 `types.ts`、`game.ts`、`App.tsx`、`formats.ts`、`compact-index.ts`、`position-search.ts`、`analysis.ts`、`vcf.ts`、`puzzle-ai.ts`、存储和测试。
- 搜索固定十五路假设，确认当前至少存在这些硬编码：`boardSize: 15`、`BOARD_SIZE = 15`、SVG 15×15 网格、`row * 16 + col` 紧凑编码、SGF `SZ[15]`、225 点扫描以及 AI/VCF 的十五路边界。
- 检查现有注释实现，确认工具栏外仍有独立的 `.comment-review` 第二行；棋子角标目前是圆形加尾巴，但没有用户要求的三个横向点。
- 评估图像识谱方案：棋盘直线检测、透视校正和浏览器本地模型推理都有成熟技术基础，可以实现可用版本；但不同图片质量下必须提供置信度和人工校正页。

## 总体实施顺序

建议按以下顺序执行，因为图像识别输出依赖动态棋盘模型：

1. 先完成注释 UI 快速修正并建立视觉回归基线。
2. 再完成动态棋盘底层改造和非十五路导入。
3. 最后接入图像识谱，使识别结果直接生成新的动态尺寸 `GameDocument`。

不要先写一个只会生成十五路结果的图片识别器，否则第二项完成后还要重写识别数据结构。

## 任务一：棋谱图像识别

### 可行性与不可伪造的边界

可以实现，目标应分成三级：

1. **无数字棋盘图**：识别棋盘尺寸、黑白棋位置，生成“当前局面”。只能用根节点 `setup` 保存最终局面，不能声称恢复了真实走棋顺序。
2. **完整连续数字图**：数字能组成唯一且连续的 `1..N` 时，按数字建立第 1 手到第 N 手的主线棋谱。
3. **数字残缺或低置信度图**：显示识别结果和问题点，允许用户修改数字、颜色和交叉点；确认后再生成棋谱。不得自动补猜缺失顺序并冒充完整结果。

单张没有数字的终局图，可能对应大量不同历史顺序，算法无法唯一反推。这是信息缺失，不是模型强弱问题。

### 推荐识别流水线

#### A. 图片预处理

- 新增图片入口，支持相册和手机拍照：`image/png`、`image/jpeg`、`image/webp`。
- 读取 EXIF 方向，限制最长边并在后台线程缩放，避免大图卡住主线程。
- 灰度化、局部对比度增强、去噪和边缘检测。
- 整个识别过程默认本地完成；不上传用户图片。

#### B. 棋盘区域与尺寸

- 使用边缘检测和 Hough 直线检测寻找两组近似平行的横纵线。
- 聚类等间距直线，推断交叉点数量和候选棋盘尺寸。
- 对倾斜拍照图计算四角并进行透视变换，校正为正方形俯视棋盘。
- 优先支持 9、13、15、19 路；底层允许 5–25 路正方形棋盘。
- 自动判断不确定时，必须让用户选择尺寸并拖动四角校准。

#### C. 黑白棋识别

- 按校正后的每个交叉点裁剪小块。
- 第一版可以组合亮度、饱和度、圆形区域占比和局部对比度，区分空点、黑棋和白棋。
- 对照片、木纹、阴影和带数字棋子，建议增加一个小型三分类 ONNX 模型；模型应懒加载并放在 Web Worker 中运行。
- 每个交叉点都保存分类概率，不只保存最终类别。

#### D. 数字与顺序识别

- 仅对已判断为棋子的交叉点裁剪数字区域。
- 分别处理黑棋白字、白棋黑字两种极性，并做二值化、放大和锐化。
- OCR 字符集限制为数字，候选范围限制为 `1..棋子总数`，不要跑通用中文 OCR。
- 如果通用 OCR 对小数字不稳定，训练轻量数字分类/序列模型。训练数据可由本项目棋盘 SVG 批量合成，再叠加字体、颜色、模糊、透视、压缩、反光和噪声增强。
- 识别后执行结构校验：数字唯一、尽量连续、坐标不重复、黑白轮次合理；发现重复号、跳号和低置信度时进入人工复核。

#### E. 识别确认页

不能直接把识别结果写进棋谱库。需要一个确认流程：

- 原图和校正网格叠加预览。
- 显示识别出的棋盘尺寸和整体置信度。
- 点交叉点可循环切换：空、黑、白。
- 点棋子可编辑数字或清除数字。
- 支持旋转 90°、镜像、重新选四角、重新选择棋盘尺寸。
- 对低置信度点使用醒目的描边，但不要用满屏红色。
- 底部常驻“重新识别”和“确认生成棋谱”。

确认时：

- 数字完整连续：生成完整主线 `GameDocument`。
- 数字不完整：提示“只能生成当前局面”，使用根节点 `setup`，识别到的数字可保留为棋盘文字标注，但不能伪造成着法。
- 保存前仍是草稿；用户进入保存弹窗并确认后才影响棋谱库。

### 运行与体积要求

- 图片处理必须放入独立 Worker，主线程保持可操作。
- OpenCV/ONNX/OCR 资源必须按需加载，不能把大模型直接塞进首屏包。
- 首屏现有构建体积约 0.52MB；新增识别资源应独立分包并显示首次加载进度。
- 识别中允许取消；取消后释放图片位图、Canvas、Tensor 和 Worker。
- 不因一次失败保留幽灵棋谱或半成品活动记录。

### 图像识别验收语料

至少准备并提交一组可重复测试样本，不能只拿一张开发图片演示：

- 干净软件截图：15 路无数字、15 路连续数字、19 路连续数字。
- 白底打印图和木纹棋盘照片。
- 轻微旋转、明显透视、阴影、压缩模糊。
- 黑棋白字、白棋黑字、两位数和三位数。
- 部分数字缺失、重复数字、遮挡和棋盘裁边。
- 非棋盘图片，必须明确拒绝，不能生成随机棋谱。

自动测试应验证生成文档的 `boardSize`、黑白位置、数字顺序、手数、导出 SGF 和刷新恢复。视觉黑盒测试要覆盖 375×812 手机视口的选四角、纠错和确认流程。

## 任务二：非十五路棋谱

### 第一阶段支持范围

- 支持 5–25 路正方形棋盘，重点验收 9、13、15、19 路。
- SGF 支持 `SZ[n]`。
- `SZ[w:h]` 若宽高不相等，第一阶段明确拒绝；不要偷偷裁剪、缩放或居中映射。
- RenLib LIB 本身继续按十五路格式读取，不要把其字节坐标解释成其他尺寸。
- 旧 RENJU JSON 和旧本地文档缺少有效尺寸时按 15 路迁移。

### 数据模型

- 将 `GameMetadata.boardSize: 15` 改为受验证的 `number`。
- 建立统一的尺寸验证函数和常量范围，不要在各文件各写一套 `5 <= n <= 25`。
- 所有棋盘、坐标、setup、标注和搜索函数都从当前文档或棋盘数组读取尺寸。
- 新建棋谱和图片识谱确认页可以选择棋盘尺寸；默认仍为 15。

### 核心算法

- `emptyBoard(size)`、`coordinateName(position, size)`、`parseCoordinate(text, size)` 动态化。
- `boardAt`、落子、改着、禁手、胜负判断、候选分析、VCF 和做题 AI 不再依赖全局十五路常量。
- 局面搜索只比较尺寸相同的棋谱；旋转和镜像变换使用当前尺寸。
- 任何循环都不再默认扫描 225 点。
- 非十五路连珠规则需要在界面注明：局部禁手算法可以运行，但正式竞赛规则通常基于标准棋盘；不要把未经确认的尺寸称为官方标准。

### 棋盘渲染与手机体验

- SVG 网格、点击层、坐标、棋子和标注都按 `boardSize` 动态生成。
- 视口保持正方形，不能因为 19 路把整个页面撑破。
- 9/13/15 路默认适配容器宽度；19 路及更大尺寸提供清晰的放大模式和横纵滚动，保留当前缩放入口。
- 点击热区不能简单固定为当前 17px；应由格距计算，并设置合理上下限，避免相邻点重叠。
- 星位按尺寸生成：15、19 路使用常见布局；其他尺寸至少显示中心点，偶数尺寸不强行制造不存在的中心星位。
- `aria-label` 改为“十九路五子棋棋盘”等动态文本。

### 紧凑索引和兼容性

当前 `row * 16 + col + 1` 把列宽写死为 16，这是本项最大风险点之一。

- 为动态棋盘设计新的紧凑索引版本，编码必须携带或读取 `boardSize`。
- 保持旧 v2 索引按 16 步长读取，不能让升级后的代码破坏已有大型 LIB。
- 新索引可以使用固定 32 步长或基于 `boardSize` 的编码，但编码/解码必须成对并有迁移测试。
- IndexedDB 分块、Worker transfer、fingerprint 和去重签名必须包含棋盘尺寸。

### 导入导出

- SGF 导入按每棵顶层棋树自己的 `SZ` 创建文档。
- SGF 坐标验证以该文档尺寸为准；setup、move、marks 都不能越界。
- SGF 导出写入真实 `SZ[n]`。
- RENJU JSON 验证接受支持范围内的尺寸，并拒绝节点越界。
- JSON moves 适配器使用 `boardSize`；未声明时可以默认 15，但必须有提示。
- 跨尺寸重复导入不能被错误判为相同棋谱。

### 动态棋盘验收

- 9、13、15、19 路 SGF：导入、导航、创建分支、删除、保存、刷新、导出、重新导入。
- 每个尺寸测试四角、边线和中心附近坐标。
- setup、pass、标注、注释、旋转、镜像和跨谱搜索。
- 旧十五路普通棋谱、旧大型 LIB、旧紧凑索引必须回归通过。
- 手机 320、375、430px 三种宽度测试 19 路棋盘，不得出现按钮挡住棋盘、无法点边缘交叉点或页面横向整体溢出。

## 任务三：注释入口与角标

### 工具栏位置

当前有注释时，注释入口不应继续单独占据 `.comment-review` 第二行。

- 当当前节点存在注释时，在 `.workspace-status` 内部的 `.record-command-bar` 最左侧显示注释按钮。
- 最终顺序必须是：`注释` → `保存` → `删除` → `黑白/锁定切换组`。
- 没有注释时不显示这个常驻注释按钮，不留下空白占位。
- 注释按钮与保存、删除属于同一视觉层级，尺寸约 40–44px，点击区域不得小于 40px。
- 按钮不要写“注释”文字，使用简洁图标和无障碍标签。

### 展开行为

- 点击工具栏注释按钮后，在状态栏下方展开当前节点注释正文。
- 展开时下方 `.context-dock` 暂时折叠，避免注释与操作面板同时挤占手机高度。
- 再点一次恢复原先操作面板。
- 切换节点时自动收起，避免把上一手的展开状态误认为下一手注释。
- 编辑或删除注释后，按钮和棋子角标立即同步出现或消失。

### 棋子右下角角标

当前棋子有注释时，在该棋子右下角显示小型注释标记；只标当前这一步对应的棋子。

- 保留高对比的小圆形或微型对话气泡底，不使用大号 Lucide 图标。
- 图标内部是三个横向排列的小圆点：`•••`。
- 三个点必须在 375px 手机视口清楚可见，不能缩成一条线。
- 黑棋、白棋和开启/关闭手数时都要有足够对比。
- 角标不得遮住主要手数；位置以棋子右下缘为主，必要时轻微越出棋子边界。
- 标记 `pointer-events: none`，不能抢走棋盘点击和长按。
- 删除当前节点注释后角标立即消失。

### 注释交互验收

- 当前节点有注释：工具栏最左出现注释按钮，棋子右下出现 `•••` 角标。
- 当前节点无注释：两处均不出现。
- 展开注释时下方操作区折叠；收起后恢复。
- 前后导航、切换分支、删除注释、保存、刷新后状态正确。
- 320×568、375×812、430×932 视口截图对比，工具栏不能换成第二行，也不能压住状态文字。
