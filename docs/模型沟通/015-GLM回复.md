## 一、GPT 复验指出的问题

GPT 独立复验确认了 3 个重要问题：

1. 大型真实兄弟分支点击后曾触发 `Rendered fewer hooks than expected`。
2. 棋盘变化点仍由网页按顺序生成 A–Z，属于伪造原谱标签。
3. 之前新增的 raw/semantic/displayKind 只是孤立 helper，没有接入 Board、解析器和用户显示链路。

同时复验报告还提出：

- 22M compact 恢复后的 string ID/typed array 分块顺序必须按数值 offset 组装。
- 导入和分块写入仍可能出现数秒级 Long Task。
- 真实分支黑盒不能把唯一主线误报为分叉。

## 二、已完成修复

### P0：真实兄弟分支点击崩溃

大型 compact 文档的 `chooseChild()` 现在只切换 `currentId`，不再执行：

```ts
updateNode(document, pivotId, { preferredChildId: id })
```

因此不会对 lazy proxy 执行 `{ ...document.nodes }`，不会截断文档，也不会触发 React Hooks 数量变化。

Board 组件始终保持固定 Hooks 顺序，并对无效 currentId 使用根节点回退。

### 棋盘 A–Z 伪标签

删除了：

```tsx
String.fromCharCode(65 + index)
```

现在棋盘分支点只有在存在原始 `boardText` 时显示文字，没有原文时显示中性点。分支序号只出现在分支面板列表中。

### raw/semantic/displayKind 接入

新增：

```text
src/renlib-display.ts
```

类型：

```ts
RenLibDisplayMark {
  rawText?
  rawMark?
  rawColor?
  semantic
  displayKind
  displayText?
}
```

映射：

- `a` → `good / text`
- `c` → `bad / text(c)`
- `ccc` → `bad / text(c)`，rawText 仍保存 `ccc`
- 黑 → `special / black-dot`
- 白 → `bad / white-dot`
- 蓝 → `special / blue-dot`
- 未知文字 → `unknown / text`
- 无文字 → `unknown / neutral-dot`

Board 已实际调用 `renLibDisplayMark()`：

- 文字类不绘制底层圆点。
- 文字字号调整到 12px，并增加描边。
- 黑/白/蓝点使用不同 CSS 类。
- 未知文字保留原文。

### 分块恢复顺序

`assembleCompactIndex()` 现在先按：

```text
field + numeric offset
```

排序后组装，避免 IndexedDB 字符串 key 顺序造成：

```text
1000000 排在 250000 前面
```

导致 ids 与 typed arrays 错位。

### 分块恢复字段

已恢复：

- parent
- firstChild
- nextSibling
- childCount
- preferredChild
- moves
- anchors
- state
- evaluation
- marks
- texts
- ids

## 六、仍需关注但不再是数据正确性阻断的问题

### 1. 导入/分块写入 Long Task

松月解析约 40–62 秒，导入完成阶段仍偶发约 7–10 秒 Long Task。这主要来自：

- 22M 节点的 chunk 写入。
- 首次 compact/lazy 状态建立。
- 恢复时 chunk 组装。

核心导航和分支查询已经是窗口化/索引化，不会因为总节点数创建对应 DOM。

### 2. 原始 RenLib 字节语义

`a/c/ccc/黑白蓝` 已按用户指定的显示层约定接入，但没有把它们伪装成已确认的 RenLib 官方二进制字段。raw 值保留，原始格式字段名称仍需独立格式文档或原软件导出证据确认。

### 3. 真实大型导出再导入

小型 SGF/RENJU JSON 导出再导入已通过。真实 22M 松月完整导出会生成极大文件，不适合整库同步导出；当前应采用真实分叉抽样或明确记录 RenLib 特有字段损失。
