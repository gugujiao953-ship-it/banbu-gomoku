## 三、阻断问题

### P0：大型谱点击真实兄弟分支后应用崩溃

独立定向验收定位到松月首个真实分叉：

- firstBranchId：存在。
- childCount：60。
- 面板提示：`当前支点后续有 60 个变化`。
- 首屏实际渲染：9 行，证明固定窗口虚拟化生效。
- 面板打开耗时：约 146 ms。
- 点击第 2 个分支后报错：`Rendered fewer hooks than expected`。

根因链路：

1. `chooseChild()` 为设置默认主线调用 `updateNode()`。
2. `updateNode()` 执行 `{ ...document.nodes }`。
3. 大型 lazy nodes Proxy 的 `ownKeys()` 对超过 10 万节点返回空数组。
4. 新 document 因此只剩被 patch 的支点，选中的 child 不再存在。
5. `Board` 收到不存在的 currentId，`current` 为空，在部分 Hooks 之前提前 return，触发 Hooks 数量不一致错误。

这不只是“设置默认主线”问题。大型 lazy 文档上的注释、标注、改着、加分支和删除变化也依赖对象展开或全量枚举，存在同类数据丢失或不可用风险。原目标要求的“任意分支可点击跳转”和“叶节点查看兄弟变化”因此没有完成。

### P1：松月仍有明显主线程卡死

本次实测最大 Long Task 为 8.25 秒。可能的主要同步来源包括：

- 主线程 `createLazyDocument()` 再扫描 2200 万节点计算 branchCount。
- 2200 万条字符串 ID 的结构化克隆、切片和 IndexedDB 写入。
- `saveCompactIndex()` 在一个同步循环内切分所有 typed arrays、ids、texts 和 marks 并连续 `store.put()`。

这违反“导入期间 UI 持续响应、无明显卡死”和“连续导航偶发不超过 50 ms”的验收要求。

### P1：现有大型黑盒存在假阳性

`qa/large-lib-blackbox.mjs` 在调用 `__banbuFindBranch()` 后又点击“到第一手”，把定位结果重置到根节点；随后正则 `/后续有 [1-9][0-9]*/` 会接受“后续有 1 个变化”。因此原报告里的 `clicked: true` 只是点击了唯一主线，不是兄弟分支。

脚本还没有断言：

- childCount 必须大于 1。
- 面板总数等于真实 firstBranchChildCount。
- 点击前后 currentId 与末手坐标变化。
- 叶节点重新打开面板仍能看到父节点兄弟。
- 刷新后重复上述分支断言。

### P1：a/c/ccc/黑白蓝点显示语义未实现

`009-GPT总任务验收.md` 明确要求数据结构保留 rawText、rawMark、rawColor/status、semantic 和 displayKind，并测试 a→good、c/ccc→bad、黑白蓝点样式和 unknown。

当前 `types.ts` 与解析器没有这些字段和映射，只有 `renLibMark: boolean`。定向松月测试仍读到并直接显示类似 `H8\b黑胜\ta\t白输\tc` 的原始控制文本，说明 a/c 仍作为普通字符串进入 UI。34 个测试中也没有上述语义测试。

### P2：compact 架构仍保留 2200 万字符串 ID 与线性查找

虽然父子关系已经是整数索引，但 `RenLibArrayBuilder.toIndex()` 仍为每个节点创建字符串 ID；Worker 传输时 typed arrays 使用 transferable，`ids: string[]` 仍需结构化克隆。`compactNodeIndex()` 还使用 `index.ids.indexOf(id)`，最坏为 O(2200 万)。

这与最终报告所称“去掉 string ID 索引、改为纯整数 nodeIndex”并不完全一致，也是内存、传输和深层随机跳转的潜在瓶颈。

### P2：严格统计和真实导出回归仍不完整

- 解析器内部计算了 edgeCount、maxChildren、maxDepth，但最新 GLM 报告没有给出松月完整矩阵和结构一致性校验。
- 没有记录 compactBuildMs、IndexedDB writeMs、openMs。
- SGF/RENJU 导出再导入只测试了人工构造的 3 节点小树，没有按任务单对雨/松月真实分叉抽样并比较父子关系、注释、boardText、评价、标记和字段损失。

## 四、已确认做得好的部分

1. RenLib 解析已从完整 `RecordNode` 对象树改为 parser-owned 列式数组，解决了 V8 大对象属性上限。
2. Worker 使用 transferable 传输主要 typed-array buffer，避免完整 GameDocument 克隆。
3. IndexedDB compact 分块保存和刷新恢复在两份真实大谱上成功。
4. 大谱分支总数能从 compact 索引取得；松月首个真实分叉的 60 个子节点可被正确识别。
5. 分支面板固定窗口有效：60 个分支只渲染 9 行，DOM 约 492–497，不随总节点数线性增长。
6. 基础测试、构建、PWA 体积和两种手机视口均稳定通过。

## 五、下一步修复顺序

1. 为大型 compact 文档实现 overlay/edit layer，禁止对 lazy Proxy 执行对象展开；分支跳转本身不应通过破坏整个 document 来设置 preferredChild。
2. 修复 `Board` 在 Hooks 中途条件 return 的规则问题，并增加大型真实分支点击回归测试。
3. 修复大型黑盒：真实跳到 firstBranchId，要求 childCount > 1，断言点击前后 currentId/坐标与叶节点兄弟切换。
4. 将 UI 当前状态逐步改为 nodeIndex，按规则生成显示 ID，避免 2200 万字符串 ID 和 `indexOf`。
5. 将 branchCount 直接使用 parser stats，分块 IndexedDB 写入分帧/分事务，重新测量并消除 8.25 秒主线程 Long Task。
6. 按任务单实现 a/c/ccc/黑白蓝点的 raw + semantic + displayKind 数据模型和测试。
7. 对真实雨/松月分叉做 SGF 导出再导入抽样回归，明确 RenLib 专有字段损失。
