## 本轮重要结论

GLM 已发现一个非常关键的潜在问题：

此前 Worker 可能直接 postMessage 一个带 Proxy 的 lazy document，这可能导致结构化克隆失败、结果被截断或 App 收到的文档不完整。

现在已经改为：

    Worker:
      plain metadata + compactIndex
        ↓
    App:
      createLazyDocument(base, compactIndex)

这是正确方向。

但 007-GLM回复中的最新结果仍然是“旧等待逻辑”产生的结果：

- importDiagnostic: null
- branchDiagnostic.hasCompact: false

因此这些结果不能用来判断新协议是否失败。本轮必须用最新 Worker、新 App、新黑盒等待逻辑重新启动和测试。

## 结果分流

### A. importDiagnostic.hasCompact = false

立即检查：

- 松月.lib 是否走了 Worker。
- 文件扩展名是否仍为 .lib。
- 文件大小是否触发大型路径。
- Worker 是否返回 result。
- compactIndex 是否为空。
- compactDiagnostic 是否在 Worker 内部由实际 index 生成。
- App 是否在错误分支中覆盖了诊断状态。

### B. importDiagnostic.hasCompact = true，但 App branchDiagnostic.hasCompact = false

问题在 App 接收、重建或打开路径。

必须记录：

- Worker 诊断。
- parseRecordFile 收到的诊断。
- saveCompactIndex 前诊断。
- loadLargeDocument 后诊断。
- openRecord 后诊断。
- window.__banbuFindBranch 调用时诊断。

重点排查：

- App 是否用 compactIndex 重新 createLazyDocument。
- resolvedSingle 是否仍然是普通 result.document。
- duplicate/fingerprint 是否打开旧文档。
- largeImports 的 index 和 result 是否错位。
- 当前 document 是否被 immutable spread 成普通文档。
- WeakMap key 是否失效。

### C. 两边 hasCompact = true，但 firstBranchId = null

说明需要检查实际索引和 RenLib 父子结构：

- childCount。
- firstChild。
- nextSibling。
- rootFirstChild。
- DOWN / RIGHT 控制记录。
- 分叉节点扫描范围。
- 是否把非落子节点误当成树边或跳过了真实分支。

不要继续只改 QA 定位器。

### D. 两边 hasCompact = true 且 firstBranchId 有值

必须完成真正的 UI 强验收：

- 调试接口跳到 firstBranchId。
- 面板总数等于 firstBranchChildCount。
- 真实分支行数大于 0。
- 首行坐标正确。
- 点击第二个兄弟分支。
- currentId 改变。
- 最后一手坐标改变。
- 进入叶节点。
- 叶节点可以看到父分叉点的兄弟变化。
- 刷新后再次验证相同结果。
