## 二、根因与修复

### 根因：canonical key 的比较算法与参考站不一致（src/formats.ts `dpCanonicalKey`）

旧实现把 8 个对称变换后的落子序列 `join(",")` 后做**字符串比较**来选最小变换；参考站（Rapfi `dbTypes.js` 的 `compareStones`）用**数值对比较** `x*32+y`。当坐标出现两位数（K–O 列，即 10–14）时两种序不同：字符串序 `"10" < "2"`，数值序 `10 > 2`。一旦两种序给出不同的最小变换，我们算出的 canonical key 与数据库存储键不一致，`queryDpPosition` 就查不到**数据库里真实存在**的子记录。

表现即用户所见：分支点坐标在 K–O 区域附近的分支（包括带 A 标注的分支）整支消失；走到这类“终点”后没有可切换的兄弟、只能结束浏览；导出的投影/JSON 也随之缺支。

真实数据量化（修复前，九天指南v4-2.db，20000 个可达局面）：240 个局面的分支坐标集合少于参考站，24 个局面的标签不一致；共 1990 个局面存在至少一处差异。修复后全部归零。

### 修复内容（src/formats.ts，一处函数）

1. 新增 `dpStonesCompare`：按参考站语义做数值对比较（0xFF 视为 -1）。
2. `dpCanonicalKey`：改用 `dpStonesCompare` 选最小变换（`<= 0` 替换，平手取后者，与参考站 `smallStones` 一致）；并补上参考站 `getStones` 的过手占位（黑白子数与行棋方不匹配时补 0xFF 对），保证生成的键与参考站逐字节一致。
3. 其余 DP 管线（对称展开、@BTXT@ 标签、record 解析）经对照确认与参考站语义一致，未改动。

## 四、关于“导入 lib 节点显示不全”的排查结论

1. 移植层核对：`src/renlib-web/` 与参考站 `ReadLib/script/` 逐文件 diff，核心文件（RenjuLib.js、RenLibDoc.js、RenLibDoc_wasm.js、LibraryFile.js、MoveNode.js、RenLib.wasm 等）**逐字节一致**；`RenjuLib_worker.js` 的差异仅为 requestId 应答管道，不影响解析与分支枚举。
2. 端到端：瑞星谱与雨.lib 的 DOM 分支标记与参考站核心（同一份 RenLib.wasm 在 Node 沙箱运行，`tmp/oracle/lib-oracle.mjs`）100% 一致，未发现节点缺失。
3. 发现一个真实环境坑：`/renlib/*` worker 资产由 vite 插件**构建期**拷贝到 `dist/renlib/`；`vite dev` 开发服务器不执行 `generateBundle`，因此在 dev 模式下打开 .lib 会失败（页面停在“正在后台解析”）。生产构建、预览与 APK 不受影响。后续若要在 dev 模式调试 LIB，需要给 dev server 增加同路径的静态资产中间件。
4. 历史“节点显示不全”如果发生在 DP 混合浏览或由 DP 投影导出的 JSON 上，与本轮 canonical key 根因同源，已随之修复；纯 LIB 场景本轮在两个真实库上未能复现缺失。
