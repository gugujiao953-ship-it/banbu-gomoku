## 一、本次纠偏结论

我们前面的工作有一部分已经偏离用户真正想要的目标。

用户要的不是“内部已经使用了 Worker、compact index、lazy document、IndexedDB”，也不是“某几个大文件能够导入并且测试通过”。用户真正想要的是接近 `renjutool.top` 的最终使用体验：

```text
多大的真实棋谱都尽量能够导入
导入后可以稳定浏览、切换分支、前进、后退和刷新恢复
页面不能出现长时间卡死、错误跳转、棋子消失或异常空白
原始 LIB 中的注释、节点文字、变化标签和标记要在用户界面中正常显示
不能因为字段被放进 boardText 而让用户在注释界面看不到它
```

因此，第 44 次回报只能算“底层链路取得进展”，不能算达成用户目标。

## 二、对第 44 次 GLM 回报的重新判断

### 1. 大谱导入仍不能称为“无异常”

第 44 次回报明确记录：

```text
17M 节点导入约 61 秒
最大长任务约 7.7 秒
个别后退操作 396–684ms
```

这已经属于用户可感知的异常，尤其是 7.7 秒长任务。即使最终 `consoleErrors=[]`、节点数正确，也不能写成接近目标网站的流畅体验。

后续报告必须把以下指标列为失败或风险，而不是隐藏在“导入成功”后面：

- 首次可交互时间；
- 文件选择后页面是否长时间无响应；
- 导入期间是否能显示进度；
- 7.7 秒级 Long Task 是否仍存在；
- 前进、后退、跳分支的最大延迟；
- 失败时是否能取消、重试和保留已有棋谱。

### 2. “注释没有丢”不等于用户能正常看到注释

GLM 证明了 `comment` 和 `boardText` 在 compact、Worker、IndexedDB、lazy rehydrate 中仍然存在，但这只证明存储链保留了字段。

用户反馈的是：导入后某些位置只有节点，原生注释看不到。若当前 UI 只把 `comment` 放进注释面板，而把大量 `boardText` 只用于节点标签，那么用户体验仍然是不完整的。

不能用下面这句话结束问题：

```text
原文件保存的是 boardText，不是 comment，所以不是丢失
```

产品上必须解决的是：

1. 当前节点的所有原始文字都能被用户找到；
2. 注释面板应明确区分“普通注释”和“节点文字/变化标签”，但不能默认隐藏后者；
3. 分支点、节点列表和棋盘上的原生标记要保持一致；
4. `a/c/#` 等内容暂时没有确定语义时，显示原始值，不得静默改成错误含义；
5. 如果原软件把某类内容显示在棋盘或分支列表中，网页也要有对应的可见位置。

### 3. 不能只参考网站的架构，还要参考网站的行为

目前的对比重点偏向：

```text
Worker / WASM / TypedArray / Canvas / IndexedDB
```

但用户关心的是：

```text
导入什么文件
导入后看到什么
注释在哪里
分支如何显示
点击节点后是否准确到达对应局面
大文件操作时页面是否还能正常响应
```

`renjutool.top` 应作为产品行为基准，不只是技术架构参考。必须建立同一文件、同一节点、同一分支的对照记录，不能只凭公开代码结构推测体验。

## 三、下一阶段必须调整的验收标准

### A. 建立真实文件验收矩阵

至少使用：

```text
雨.lib
松月.lib
瑞星棋谱（适合新手+标注详细）.lib
用户提供的带详细节点文字和分析标记的真实 LIB
用户提供的 .db/.dp 文件
```

每个文件都要记录：

- 文件大小；
- 总节点数；
- 分支数；
- 最大深度；
- 普通 comment 数量；
- boardText 数量；
- 原始标记数量；
- 首次可交互时间；
- 导入总耗时；
- 最大 Long Task；
- 前进/后退/分支切换最大耗时；
- 刷新后是否恢复同一节点和同一注释；
- 是否出现棋子消失、跳错终局、空白、异常提示或页面冻结。

### B. 建立“原生内容可见性”验收

不能只检查 IndexedDB 中有字段，必须在浏览器页面中逐项确认：

```text
原始 comment → 用户能看到
原始 boardText → 用户能看到
节点文字/变化标签 → 分支列表或节点详情能看到
原始标记 → 棋盘、节点或详情中能看到
```

随机抽取至少 20 个包含文字的真实节点，保存以下证据：

```text
原始 LIB 节点 ID
原始字段值
网页当前节点 ID
网页显示文字
网页显示位置
```

如果网页显示为空，即使 IndexedDB 有值，也必须判定为用户体验不通过。

### C. 大谱“可用”不能只等于“能导入”

对于 1700 万节点文件，必须验证导入之后连续执行：

1. 打开根节点；
2. 前进 20 步；
3. 后退 10 步；
4. 进入多个真实分支；
5. 从叶节点切换到兄弟分支；
6. 打开节点文字/注释；
7. 刷新页面；
8. 重新打开同一棋谱；
9. 导出再导入；
10. 在页面仍可响应的前提下执行新增草稿和放弃草稿。

任一步骤出现错误、卡顿到无法操作、节点跳错、文字不可见，都不能标记为“完成”。

## 四、必须停止的错误表述

后续不要再把以下表述当作最终结论：

```text

P95 较低，所以大谱体验已经达到目标

```

正确表述应区分：

```text
底层解析通过
数据存储保真通过
页面可见性通过
真实交互通过
大文件性能通过
最终产品验收通过
```

只有最后一项也通过，才能说达成用户目标。
