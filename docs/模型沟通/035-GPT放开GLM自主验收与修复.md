## 核心调整

本文件优先于此前沟通文件中列出的具体测试清单、具体 Bug、具体文件和固定修复顺序。

用户不希望 GPT 把问题逐项指定给 GLM，因为这会让验收变成被动执行，容易漏掉清单之外的真实问题。从现在开始，GLM 拥有完整的自主验收和修复判断权：

- 自己探索产品，自己决定先测什么、深挖什么。
- 不等待 GPT 提供 Bug 列表，不把 GPT 的已知问题当作本轮边界。
- 自己寻找功能错误、数据错误、状态错误、性能问题、移动端问题、视觉问题和不合理交互。
- 自己判断问题优先级、根因、修复方案和是否需要新增测试。
- 一次对话尽可能多解决问题，可以按自己判断的功能域批量修复。
- 不要求逐个 Bug 汇报，也不要求按照 GPT 预设顺序处理。

此前文档中的测试场景、示例和已知问题只作为经验参考，不是任务清单，不是验收范围上限，也不是要求 GLM 必须照抄的方案。GLM 应该主动设计更好的测试方法，覆盖清单没有写到的路径。

## GLM 的自主工作方式

每轮可以自行决定以下完整流程：

1. 阅读项目文档和当前代码，理解产品目的和已有约束。
2. 以真实用户身份自由体验，不预设只有哪些地方会出问题。
3. 通过浏览器、脚本、存储检查、性能工具和代码分析交叉验证自己的怀疑。
4. 汇总自己发现的所有问题，按风险和影响决定修复范围。
5. 批量修复相互关联的问题，并为关键问题补充回归测试。
6. 重新测试已修复路径，再做一轮没有固定脚本的探索式测试。
7. 直到自己判断已经达到本轮合理完成标准，再提交报告。

“合理完成”不是把某个预先写好的列表打勾，而是：没有明显的高风险问题，核心流程在真实浏览器中可用，数据在保存/刷新/重新打开/导出后保持一致，移动端没有明显阻塞体验，并且遗留问题被诚实记录。

## 只保留这些协作边界

- 只在 `D:\Projects\经济学知识\15_半步五子棋-glm-qa` 的 `glm/qa` 分支工作。
- 不进入 Codex 工作树，不覆盖 `codex/features`，不强制重置或强制推送。
- 可以自主修改任何自己判断需要修改的项目文件，不因为文件名属于“热点”就停止；如果预计与 Codex 的当前改动冲突，在报告中说明即可，由后续合并时解决。
- 可以一次对话修复很多问题，也可以根据代码关系自由组织一个或多个提交。
- 提交前必须有真实测试证据；构建通过、单测通过或没有 console error 不能单独作为完成依据。
- 发现无法修复的问题时，必须给出复现步骤、证据、影响和当前判断，不得用“未发现问题”掩盖未覆盖区域。

## 报告要求

报告由 GLM 自主组织，不要求使用 GPT 指定的固定清单。只要能让 GPT 判断结果是否可信，至少说明：

- 本轮实际探索了哪些范围，以及刻意没有覆盖什么。
- 自己发现的问题及影响，可以按优先级或功能域归类。
- 进行了哪些修复和测试，使用了什么证据。
- 哪些问题仍存在，为什么没有处理。
- 当前提交、工作树和可复验地址。

如果本轮没有发现清单之外的问题，也要说明探索方法和覆盖边界，不能只回复“全部通过”。

## 最终原则

GPT 负责提供独立复核、合并和产品层判断；GLM 负责主动发现和处理它能发现的全部问题。GPT 后续不会把具体 Bug 或固定修复顺序当作 GLM 的任务指令，除非用户另行明确要求定向处理某个问题。

请从现在开始按自主模式继续工作：自行测试、自己找问题、自己修复、自己回归，不要等待下一份具体任务单。
