## 一、产品现状快照

一句话：**格式兼容与大谱浏览已达业内第一梯队，打谱核心闭环完整，但"表达与分享、AI 深度、学习闭环、视觉个性化"四个维度明显落后于竞品的最好水平。**

| 维度 | 现状 |
|---|---|
| 平台 | PWA + Android（Capacitor 8），一套 React/TS 代码；无 iOS/桌面 |
| 打谱 | 变化树、分支面板、书签、注释/标注/评价、查找、跨谱局面检索（雏形）、旋转镜像、开局规则（两打/多打/塔拉山口/Tarannikov） |
| 格式 | 导入 SGF/JSON/POS/RENJU/LIB(动态 WASM)/DP/DB；导出 SGF/JSON + 原格式直出；不能写回原生格式 |
| 大谱 | 1.185GB 斜月.lib 实测 39 秒可交互；DP 与 renjutool oracle 100% 对齐（052） |
| 做题 | 开宝兼容题库 436 题 + RenjuPortal 等外部题集；本地 AI 陪练；无答案线/错题本/统计 |
| AI | 本地 Rapfi WASM（人机）+ 自研 alpha-beta + VCF（带独立证明校验）；强度基准未完成 |
| 存储 | localStorage + IndexedDB compact index；草稿/派生版本；无全量一键备份 |
| 外观 | 单一浅色主题；无暗色模式、无皮肤、无分享图片/GIF |
| 工程 | 128 单测 + 大量 Playwright QA；tag 触发的 Android 发布 CI；无 push 质量门禁 CI |

## 二、六视角评审

### 2.1 全栈工程师：架构与代码

**做得好**：Worker 边界清晰（AI/VCF/DP/RenLib/导入各自独立），大文件不卡主线程；格式层是纯函数、与 UI 解耦；`GameDocument` 单一文档模型贯穿三端；存储按大小分级（localStorage/IndexedDB）。

**问题**：
1. `src/App.tsx` 2212 行单组件，30+ useState，打谱/做题/人机三套状态机交织。历史上"草稿串谱""保存回旧版本"等多轮严重 bug 均出自这里。**这是最大的回归风险源**。
2. `package.json` 核心依赖全部 `"latest"`（react/vite/typescript/@vitejs/plugin-react）。虽有 lockfile，但任何一次重装都可能引入 breaking change，且 CI 与本机构建可能漂移。
3. 无顶层 ErrorBoundary：任何一个渲染异常=整页白屏（PWA 下用户只能清缓存）。
4. dev 模式 `/renlib/*` 资产 404（vite 插件只挂了 `generateBundle`，052 已记录）：开发调试 LIB 必须先 build，浪费每轮验证时间。
5. 动态视图会话（DpViewSession/RenLibWebViewSession）的 Worker 生命周期靠手工 close，切换谱/退出路径多，泄漏靠自觉。
6. 无路由：刷新恢复靠存储游标，无法"分享一个局面链接"。

### 2.2 软件设计工程师：数据、格式与正确性

**做得好**：DP canonical 修复后与参考站逐局面 0 失配（052 建立了可回归的 oracle 基线，业内罕见）；导入校验严格（树结构/循环/孤立节点/坐标越界全查）；诚实边界——不伪造不支持的转换。

**问题**：
1. **AI 强度没有正式结论**：`scripts/benchmark-ai.mjs` 仍是 `maxSteps: 10`（用户最终要求 15），完整高级题集基准从未跑过。对外不能声称棋力，对内无法分级。
2. **禁手非裁判级**：跳三、假活三、双四同向/异向、边界形状缺黄金用例；产品文案与实际能力边界需保持一致。
3. **LIB/DP/DB 编辑不能写回原生格式**：开库维护者（如九天指南作者型用户）编辑后只能导出 SGF/JSON，回不到自己的库——这是核心专业用户的硬伤。
4. 文档口径漂移：README 说"固定十五路，其他 SZ 拒绝"，代码 `isSupportedBoardSize` 支持 5–25；端口、功能清单多处过期。
5. 无全量一键备份/恢复：换机迁移 = 手工逐个导出；IndexedDB 里的大谱索引尤其无助。
6. 不支持 ZIP 包批量导入（明确拒绝并提示解压），对动辄几十个文件的棋谱包不友好。
7. 图片识谱准确率低（主聊天正在攻关，本计划只挂依赖不重复展开）。

### 2.3 交互体验设计师

**做得好**：棋盘优先 + 底部工具坞 + 44px 触控原则贯彻一致；草稿离开拦截、防误触、数据库终点"继续编辑"等专业细节到位；外接键盘方向键支持。

**问题**：
1. **无落子动画、无触觉反馈、无分支切换过渡**——对比 BadukPop/主流棋类 App 的"手感"差距最直观的一项。
2. 无手势体系：双指缩放（大谱 650px 宽横向滚动很笨重）、左右滑动切手数。
3. 首次使用零引导：功能藏在"更多/设置"深处（分支书签、跨谱检索、书签图标含义），无发现机制；帮助只有静态文字。
4. Android 返回键语义未验证（真机测试一直"未完成"）：用户预期返回=悔一手或关面板，实际可能直接退出应用。
5. 删除棋谱/题集无回收站，误删不可恢复。
6. 导入无"最近文件"、无剪贴板 SGF 粘贴、无 URL 拉取（renjutool 三者都有或部分有）。
7. 平板/横屏：520px 手机壳在平板上两侧大量留白，无双栏利用。

### 2.4 UI 视觉设计师

**做得好**：墨绿+宣纸木色品牌语言统一且有辨识度；serif 标题、迷你棋盘缩略图、AI 思考流光等细节有版本感。

**问题**：
1. **无暗色模式**。夜间打谱是高频场景（比赛复盘、被窝做题）；`styles.css` 仅有 9 个 CSS 变量，主题化地基薄。
2. 竞品信号明确：renjutool 有 4 套主题 + 主题编辑器，我们的测试资料里就有用户自制的"仿五林主题"JSON——**用户在主动要主题系统**。
3. 信息密度过高：命令条 6 按钮 + 底坞 5 tab + 工具坞 6 折叠组，新手认知负担大；缺少"简单模式"。
4. 大量 8–10px 字号，`#928b80 on #fff` 对比度约 3.4:1，低于 WCAG AA（4.5:1）；无字号缩放。
5. 棋盘/棋子皮肤单一（固定木色），无质感选项。
6. 空状态千篇一律 lucide 图标，无教程性插画。

### 2.5 运维与发布

**做得好**：tag→自动构建 APK→GitHub Release 的 CI 已存在；发布物 SHA-256、签名证书管理有记录；PWA 缓存有重置入口。

**问题**：
1. 无 push/PR 质量门禁 CI（test + tsc + build 只在本机跑）——fork 协作多模型并行时尤其危险。
2. 治理前 `qa/` 目录 47 个脚本混杂正式回归与 `tmp-*` 临时脚本；`mobile-visual.mjs` 曾有已知超时问题。2026-08-29 已按 P0-6 完成分层和修复，现状见 `qa/README.md`。
3. 无诊断日志导出：用户报障只能截图，模型排障靠猜。
4. 无性能预算监控：大谱 Long Task、导入耗时等只有手工记录，无回归红线。
5. 构建环境（JDK21/SDK/签名密钥路径）依赖文档口口相传，未脚本化（`android-release.yml` 云端构建可复现，但签名密钥在本地，两者关系需理清）。

### 2.6 五子棋爱好者（专业用户）

**做得好**：大库动态浏览（1.185GB 实测可用）是同类网页产品没有的；DP/DB 局面数据库模型正确；开局规则覆盖罕见地全；本地 AI 隐私优先。

**问题（按痛点排序）**：
1. **没有分享图片/GIF**。复盘发群、发帖是棋类社区第一高频动作，renjutool 的 saveAsImage/GIF 是其用户粘性来源；我们"导出与分享"里实际没有图。
2. **只有 VCF，没有 VCT**。研究杀棋（含眠三做杀）必须 VCT；爱五子棋打谱有 VCF/VCT/VC2-4/UCT 全家桶。
3. **"思考"没有胜率**。Rapfi 已随包（用于人机），但思考面板用的是自研启发式排序——给出胜率+PV+top-N 是现代棋类 App 的标配，也是我们和 renjutool/gomocalc 体验差距最大的一项。
4. **无树形图**。分支一多，列表面板不如一棵可视化树直观（renjutool 有 tree.js，爱五子棋有分支窗口）。
5. **做题无答案线/错题本/统计**：做错不知道错哪，没有学习闭环；RenjuPortal 解题大赛题自带标准解，格式已在测试资料里。
6. **人机无分级**：只有一档，新手被虐、高手无感。
7. 无对局计时/比赛记录模式；无双人热座。
8. 无棋谱打印/批量编辑（爱五子棋有批量替换文字、清理不防守变化）。

**逐家启示**：
- **renjutool**（用户指定的体验基准）：赢在"表达与个性化"（图片/GIF 导出、主题系统、codeURL 分享、答题器生态）。我们赢在编辑与数据正确性。→ 抄"表达"，守"正确"。
- **爱五子棋打谱**：赢在专业深度（VCT 族、批量编辑、写回）。→ 它是 P2 专业路线的对照表。
- **开宝**：赢在陪练交互细节（已完成迁移）与题库运营感（星级/进度）。缺答案线是两家共同短板，是我们差异化机会。
- **Lichess**：作为免费无广告开源棋类社区的标杆，其 puzzle 生态（每日一题/错题/评分）、复盘报告（accuracy 曲线）、键盘操作、i18n 是长期对标方向。

### 第二批：20 个轻量视觉与体验增强任务

这 20 项是新增的并发候选任务，目标是让软件更有完成度、反馈更清晰、视觉更高级，但不以牺牲包体、内存和低端设备流畅度为代价。它们只先在各自独立副本/工作树中实现，完成后由主线逐项验收，通过后再合并；不得直接覆盖主工程或互相复制整套实现。

统一约束：默认不引入大型动画库、音频库、图标库或 UI 框架；动效优先使用 CSS `transform`/`opacity`、有限时长 SVG/CSS 动画；不得使用常驻高频 `requestAnimationFrame` 粒子循环；所有动效必须支持 `prefers-reduced-motion`；不得修改 DP/DB、RenLib、格式解析和大型索引核心逻辑。音效优先使用 Web Audio API 程序化合成，若确需音频文件，全部压缩资源尽量控制在 150KB 内。单项新增 gzip 体积尽量不超过 30KB，合并后 `dist` 继续满足当前 20MB 门禁，并记录构建前后体积、依赖和内存观察。

每个副本完成后必须提交：修改文件清单、独立提交号、功能截图或短录屏、测试/QA 结果、构建结果、dist 增量、是否新增依赖、性能与内存观察、未完成边界。主线验收至少检查正常路径、窄屏、低端设备、键盘/触摸操作和 reduced-motion 路径。

- 内容生态：授权清晰的开源棋谱包/题库包分发格式（含来源与许可证清单，呼应开宝题库的权利边界）。
- iOS：Capacitor 出 iOS 包（需苹果开发者账号，成本在签名与审核）。

### 明确不做

- 赛事裁判软件（定位是研究/学习工具，P2-7 只保证判定正确）。
- 自建在线对战平台与排行榜（运维与合规成本远超个人项目收益）。
- 广告/付费墙（README 承诺永久免费开源）。
