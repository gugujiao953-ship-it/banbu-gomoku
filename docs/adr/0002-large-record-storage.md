# 0002 - 大型棋谱后台解析与分层存储

**Status:** proposed
**Date:** 2026-08-24
**Spec:** README.md、PRODUCT_NOTES.md
**Deciders:** gugujiao953-ship-it

## Context

RenLib 开局库可能达到数十至上百 MB。普通棋谱原先在主线程解析，并把完整变化树写入 `localStorage`；这会触发 25MB 前端限制、阻塞手机触控，并很容易超过浏览器约数 MB 的同步存储配额。

## Decision

- 8MB 以上的棋谱文件交给独立 Web Worker 解析，主界面显示不可误解的进行中状态。
- 原始文件达到 4MB，或解析后达到 4 万节点的棋谱，作为大型棋谱写入 IndexedDB；普通棋谱继续使用现有 `localStorage`，避免一次迁移影响既有用户数据。
- RenLib 单文件入口提高到 128MB，批次总量限制为 256MB；Android 文件选择器使用通用类型，应用内部再严格校验后缀。
- 大型棋谱与普通棋谱在 UI 中合并为一个棋谱库，但自动保存、删除和启动加载分别调用对应存储层。

## Consequences

- 92MB 级 LIB 不再因为前端固定上限或 `localStorage` 配额直接被拒绝，解析期间界面仍可响应。
- 大型变化树仍会在打开时占用较多内存；后续如需支持数百万级节点，应增加 RenLib 二进制懒加载索引，而不是继续扩大完整对象树。
- IndexedDB 是异步接口，保存状态与错误提示需要独立处理；删除当前正在打开的棋谱时必须先切换到安全的新棋谱，避免自动保存把它重新写回。

## Alternatives Considered

- 所有棋谱统一迁移 IndexedDB：模型更整齐，但迁移风险与改动范围过大。
- 只提高文件大小限制：解析后仍无法写入 `localStorage`，会造成“看似支持、实际丢失”的体验。
- 把大型 LIB 永久保留为原始二进制并按需遍历：长期内存效率最佳，但需要新的懒加载棋谱接口，不适合作为本轮兼容修复。
