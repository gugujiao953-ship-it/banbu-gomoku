## 1. 项目是什么

“半步五子棋打谱”是一个移动优先的五子棋 / 连珠打谱与做题工具。

核心用途：

1. 打开已有棋谱。
2. 按手数前进和后退。
3. 查看主线和变化分支。
4. 在棋盘上研究、标注和写注释。
5. 导入、导出多种棋谱格式。
6. 在手机浏览器和 Android 应用中使用。
7. 对局面做基础候选分析和 VCF 搜索。
8. 管理本地棋谱库和题库。

项目当前使用 React + TypeScript + Vite 构建，网页版通过 PWA 支持离线运行，Android 端通过 Capacitor 复用同一套网页代码和棋谱核心。

## 2. 为什么要做这个项目

项目起点是希望把成熟桌面打谱软件的核心能力迁移到手机和网页上，同时保留棋谱文件的兼容性。

重点场景：

1. 手机上查看五子棋定式库。
2. 打开 RenLib .lib 大型开局库。
3. 在分叉处查看不同变化。
4. 研究某个局面的候选点。
5. 给棋谱节点添加注释、局面文字和评价。
6. 把研究结果保存为可跨端读取的文件。
7. 在手机上做五子棋题目。

用户尤其在意大型定式谱体验。普通小谱能导入并不代表项目完成，因为大型 RenLib 往往有几十万节点、十万级分支和大量非普通落子节点。

## 3. 产品定位和交互原则

### 3.1 产品定位

这是一个棋盘优先的研究工具：

- 棋盘是第一视觉焦点。
- 当前局面尽量始终保持在页面上。
- 变化、注释、元数据和导出功能放在底部抽屉或上下文工具坞中。
- 手机不照搬桌面软件的密集菜单，而是保留最有价值的研究能力。

### 3.2 基本交互

- 点击空交叉点：落子。
- 点击已有棋子：跳到对应手数。
- 长按交叉点：循环切换圆圈、三角、叉号、清除。
- 外接键盘左右方向键：上一手 / 下一手。
- “变化”：打开当前分叉点的后续变化。
- “研究”：改着、候选、同局、查找。
- “记录”：注释、局面文字/评价、棋谱信息、导出。
- “视图”：手数、坐标、旋转、镜像。

主要点击区域面向手机设计，目标是窄屏也能使用，通常要求触控区域不小于 44px。

## 4. 已实现的主要功能

### 4.1 棋盘和导航

- 15×15 棋盘。
- 黑白棋子。
- A–O 和 1–15 坐标。
- 显示 / 隐藏手数。
- 90° 旋转。
- 左右镜像。
- 起点、上一手、下一手、终点。
- 点击棋子跳到该节点。
- 支持当前节点的主线和变化树。

### 4.2 变化树编辑

棋谱不是简单的落子数组，而是一棵树：

- 一个节点可以有多个子节点。
- 每个子节点代表当前局面的一种后续变化。
- 可以新增分支。
- 可以将某个子节点设置为默认主线。
- 可以删除当前变化及其所有后续。
- 可以修改当前着法坐标，同时保留后续变化。
- 在变化末端可以返回分叉支点创建新变化。

### 4.3 注释和标注

节点级信息包括：

- 普通注释 comment。
- 局面文字 boardText。
- 着法评价 evaluation：
  - good：好手；
  - bad：坏手；
  - doubtful：疑问手；
  - interesting：趣着；
  - forced：胜着；
  - only：唯一手；
  - study：研究点。
- evaluationLevel。
- 棋盘标注：circle、triangle、cross、label。
- RenLib 原始标记 renLibMark。
- 非落子局面锚点 anchor。
- 起始局面标志 startPosition。

重要区别：

- 用户设置的棋盘标注属于当前节点局面。
- 着法评价属于某一个落子节点。
- RenLib 原始 mark 不一定等于用户标注。
- 非落子节点可能只是保存局面文字或标记的锚点，不能强行当成一手棋。
- 已落子点不应该再叠加后续空位标签。

### 4.4 局面分析

当前有两类分析：

1. 启发式候选排序，考虑成五、活四、冲四、活三和防守点。它用于研究和标记，不是完整的 VCF/VCT 证明器。
2. VCF 搜索，在独立 Web Worker 中运行，限制进攻手数、节点预算和时间预算，并对结果进行主线程复验。

### 4.5 棋谱库

- 普通棋谱保存于本地。
- 大型棋谱保存于 IndexedDB。
- 启动时读取大型棋谱摘要，不立即还原完整节点对象。
- 支持按名称、棋手、赛事主题搜索。
- 支持批量导入、重复检测和 ID 冲突隔离。
- 自动保存有防抖。
- 支持本地删除。

### 4.6 题库

- 打谱模式和做题模式共用一个棋盘工作区。
- 题库支持黑先 / 白先。
- 玩家落子后由 Web Worker 计算陪练应对。
- 支持悔棋、重启、停止思考。
- 支持题目完成状态。
- 支持开宝兼容二维 JSON 题库。
- 当前内置题库约 436 题。

## 5. 核心数据模型

### 5.1 GameDocument

棋谱文档顶层结构：

    GameDocument {
      id
      version
      rootId
      nodes
      metadata
      createdAt
      updatedAt
    }

其中 nodes 是节点 ID 到 RecordNode 的映射。

### 5.2 RecordNode

一个节点代表一个局面或一个落子：

    RecordNode {
      id
      parentId
      children
      move
      anchor
      comment
      marks
      preferredChildId
      boardText
      evaluation
      evaluationLevel
      renLibMark
      startPosition
    }

关键语义：

- move 不为空：该节点代表一手真正落子。
- move 为空但 anchor 存在：可能是 RenLib 保存的局面文字或标记锚点。
- children：后续变化节点 ID。
- preferredChildId：当前默认主线选择。
- parentId：回退和定位分叉点。
- comment：长文本注释。
- boardText：短局面文字或节点名。
- marks：当前局面的圆圈、三角、叉号、文字标签。
- renLibMark：RenLib 原始标记位，不能直接当成用户标注。
- evaluation：着法评价，不应随意赋予无落子节点。

### 5.3 为什么必须是树

SGF 和 RenLib 都不是单纯数组格式。

示意：

    根节点
      ├── 黑 H8
      │     ├── 白 I8
      │     └── 白 J8
      └── 黑 J8
            └── 白 I8

线性数组会丢失：

- 同一局面的多个候选后续。
- 分支父节点。
- 每个分支自己的注释和评价。
- 主线选择。
- 走到叶节点后回看兄弟变化的能力。

## 6. 文件格式和兼容性

### 6.1 SGF / FGF

支持 FF[4] 游戏树、B/W 落子、C 注释、N 局面文字、TE/BM/DO/IT 标准评价、XEV 自定义评价、CR/TR/MA/LB 棋盘标记，以及 PB/PW/EV/DT/RE/RU 元数据。

### 6.2 POS / TXT

只把 TXT 作为纯文本坐标序列兼容入口，例如：

    H8 I8 H9

它不是通用的五子棋专有格式，不能假设任意 TXT 都能还原变化树。

### 6.3 REN / RENJS / WZQ

如果内容采用 SGF 语法，则按 SGF 入口读取。

### 6.4 RENJU JSON

这是本项目自己的跨端格式，完整保存 GameDocument、变化树、注释、局面文字、评价和棋盘标记，用于网页版和 Android 未来互通。

### 6.5 RenLib .lib

RenLib 是大型五子棋 / 连珠开局库常用的二进制变化树格式。

当前代码已经尝试支持：

- RenLib 3.x 现代头。
- 旧版无头文件。
- 深度优先记录流。
- 主线和分支控制字节。
- 常见节点注释。
- 局面文字。
- 常见标记位。
- GB18030 / 旧格式文本解码。
- Worker 流式读取。
- 大型文件紧凑索引。
- IndexedDB 保存和恢复。

RenLib 的困难在于：

1. 不是简单的坐标列表。
2. 节点、分支、回退、文本和标记混合在二进制记录流中。
3. 不同版本和旧格式可能有不同头部、编码和控制字节。
4. 非落子节点可能携带局面文字或标记。
5. 原软件显示的颜色、点和文字不一定是格式标准字段。
6. 一个字节读取错位，后面整棵树都会错，表现为 ccc、缺分支或乱码。

任何 RenLib 修改都必须优先验证解析是否正确，不能只做视觉层修补。

## 7. RenLib 适配的历史背景

项目参考过爱五子棋打谱软件的功能和 RenLib / SGF 生态。

当前解释原则：

- 原软件展示的后续小点应对应当前局面的直接后续变化。
- 黑 / 白 / 蓝的视觉含义不能直接当成 RenLib 标准。
- c、ccc 等文字不能凭猜测硬编码成好手或败点。
- 原始字段尽量保留。
- 未确认标记保守呈现。
- 非落子节点和真正落子节点必须区分。

这部分仍是最需要继续逆向和压测的区域。

## 8. 大型棋谱性能架构

### 8.1 为什么普通对象树会卡

如果把大型文件全部还原成普通 JS 对象：

- 每个节点都有对象、数组和字符串。
- 每个 children 都是一整个字符串数组。
- React 或 Object.values 可能触发整棵树展开。
- 变化面板可能一次创建几十万行。
- 每一步都重放根到当前节点，复杂度随深度增长。
- 页面主线程会出现长任务。

### 8.2 当前紧凑索引

src/compact-index.ts 使用 typed array 保存：

- ids；
- parent；
- firstChild；
- nextSibling；
- childCount；
- preferredChild；
- moveCode；
- state；
- textRefs；
- texts；
- anchor、evaluation、marks 等字段。

firstChild + nextSibling 可以表达任意数量兄弟节点，而不需要为每个节点立即创建完整 children 数组。

### 8.3 Lazy Document

大型文档恢复时：

- document.nodes[id] 只在访问该 ID 时物化。
- node.children 使用惰性读取。
- IndexedDB 保存前需要显式 materialize。
- 大型棋谱优先保留 compact index，而不是完整节点对象树。

必须警惕：

- map、filter、for...of 可能触发全部 materialize。
- Object.keys(document.nodes) 可能物化所有节点。
- 旧的格式导出和局面搜索可能仍然全量遍历。
- Proxy 不是自动性能保证。

### 8.4 当前 UI 限制

当前分支面板采用首屏限量和加载更多。它只是保护措施，不等于最终理想方案。

更好的方向：

- 虚拟列表。
- 固定窗口。
- nodeIndex 查询。
- Worker 分支查询。
- 预览缓存。
- 不让总分支数决定 DOM 数量。

### 8.5 导航缓存

src/game.ts 对路径和棋盘使用 WeakMap 缓存，相同文档、相同节点不重复计算。

但 immutable update 会产生新文档对象，旧缓存不能复用。大型架构最好进一步使用稳定 nodeIndex、父节点缓存和增量棋盘。

## 9. 主要代码文件职责

### src/App.tsx

页面布局、棋盘渲染、当前文档和节点状态、打谱 / 做题模式、分支面板、变化点显示、注释、标注、评价抽屉、导入和打开、自动保存、候选分析和 VCF 入口。

这里最容易引入性能问题，因为 React render 中的任何全量遍历都会在每次导航时触发。

### src/game.ts

创建文档、创建节点、新增分支、修改着法、删除变化、路径和棋盘、主线选择、坐标转换、禁手辅助和棋盘标注。

它是通用棋树核心，不应加入 RenLib 专有解析逻辑。

### src/formats.ts

SGF 解析和导出、POS/TXT 解析、RenLib 二进制解析、编码解码、导入警告和多格式入口。

RenLib 解析应尽量与 UI 解耦，并能单独测试原始记录和节点树。

### src/compact-index.ts

GameDocument 转紧凑索引、索引恢复为 lazy document、子节点懒读取、索引统计和 IndexedDB 前物化。

### src/large-storage.ts

IndexedDB 数据库、大型棋谱摘要、紧凑索引存储、大型棋谱恢复、删除、指纹和重复判断。

### src/record-import.worker.ts

后台读取和解析文件、判断是否为大型棋谱、构建 compact index、将解析结果和摘要返回主线程。

### src/analysis.ts

启发式候选排序。

### src/vcf.ts / src/vcf.worker.ts

VCF 搜索和 Worker 执行。

### src/storage.ts

普通棋谱和本地库保存、去重、ID 冲突处理。

### src/position-search.ts

棋谱内和跨棋谱局面检索，可选旋转和镜像匹配。

### src/styles.css

手机页面、棋盘、底部工具坞、抽屉、分支列表、响应式布局和安全区。

### qa/mobile-visual.mjs

使用 Playwright 在 360×800 和 412×915 视口进行实际操作，验证落子、前进后退、研究、注释、切换题库、刷新恢复、页面宽度和控制台错误，并生成截图。

## 11. 已知边界

1. 禁手辅助不是赛事裁判级完整判定。
2. 启发式候选不是完整 VCF/VCT 证明器。
3. .lib 高版本和未知扩展可能只能保守读取。
4. .txt 只支持纯坐标序列，不是任意五子棋文本。
5. 本地保存不是云同步，需要使用 .renju 备份。
6. RenLib 的颜色和文字语义不能凭用户观察硬编码。
7. 大谱的首屏有限分支不等于分支解析完整。
8. 导入正确性、树关系正确性和显示性能必须分别验收。
9. 能构建通过不代表大型棋谱不卡。
10. 能显示一条主线不代表已经适配分支树。

## 14. 最重要的一句话

这个项目真正的难点不是画一个五子棋棋盘，而是：

> 在手机和网页环境中，正确解析大型 RenLib 变化树，并让用户在数十万节点和大量分支中仍然可以快速、准确、流畅地浏览和研究棋谱。
