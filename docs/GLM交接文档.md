# 半步五子棋打谱网页版：GLM 交接文档

更新时间：2026 年 8 月 24 日

## 1. 项目目标

本项目是 React + TypeScript + Vite 的网页版五子棋打谱工具，目标是尽可能兼容“爱五子棋”手机打谱软件读取和展示的 RenLib .lib 棋谱，尤其是大型定式库。

用户真正关心的不是“文件能导入”，而是完整体验：

1. 大型 .lib 能完整保留主线、分支、后续分支和相关标注。
2. 当前局面像爱五子棋一样显示后续可选点。
3. 每一步切换流畅，不能假死、丢点击或长时间卡住。
4. 打开分支面板不能因为分支数量巨大而卡死。
5. 已经落在棋盘上的棋子，不应再被后续变化标签覆盖。
6. 局面文字只显示当前局面相关的后续空位，不把整棵树文字堆到棋盘上。
7. 标签不要使用突兀的长方形框；除非是用户明确设置的注释/标记，否则使用轻量点、圈或文字。

## 5. 已经尝试过的架构

当前代码已经尝试：

- RenLib 在 Worker 中解析。
- 大文件保存到 IndexedDB。
- typed array 保存父节点、首子节点、兄弟节点、子节点数量、着法和文本引用。
- lazy Proxy 暴露 document.nodes[id] 和 node.children。
- pathToNode()、boardAt() 使用 WeakMap 缓存。
- 导航时不自动计算 225 个空点候选分析，只有打开“候选”面板才计算。
- 棋盘变化点只读取当前节点下一层；叶节点时读取父节点兄弟变化。
- 分支面板首屏最多显示 160 个变化，并提供加载更多。
- 分支预览只对前 80 个分支计算，预览长度限制为 3 手。
- 标签改成无矩形框，且已落子位置不显示后续局面文字。

这些改动不能直接视为最终正确，GLM 必须重新验证是否有隐式全量展开、解析错位和性能回归。

## 6. 核心历史问题

### 6.1 分支不完整

大型谱每一步后面有很多分支，网页曾经出现：

- 只能看到一条主线。
- 走到后面看不到兄弟变化。
- 后续变化点层级错误。
- 分支面板打开很卡。
- 分支显示不完整。

必须确认 RenLib 节点模型，而不是只靠 slice 截断。

### 6.2 ccc 和颜色标记

用户反馈过导入后大量标注变成 ccc，没有后续变化。

用户观察：

- 黑色点可能是可以走的点。
- 白色点可能是败点。
- 蓝色点含义未知。
- c 可能是败点。

这些只是用户观察，不是 RenLib 标准。不要硬编码为好点/坏点。必须通过真实二进制、原软件显示、导出结果和独立资料确认：

- ccc 是原始字符串，还是解析游标错位导致。
- 黑、白、蓝标记来自哪个字段。
- c 是评价、分类、board text、控制字符还是节点名称。
- 文字属于当前节点、下一手节点还是局面锚点。
- 为什么此前后续变化消失。

无法确认时必须原样保留并标记为未知，不要编造含义。

### 6.3 卡顿风险

全项目排查以下操作是否在导航/render 中触发全量实例化：

    Object.keys(document.nodes)
    Object.values(document.nodes)
    node.children.map(...)
    node.children.filter(...)
    node.children.forEach(...)
    for (const child of node.children)
    对所有分支执行 variationPreview()
    每步重新分析 225 个空点
    每次 render 递归访问完整后续树
    为显示统计而扫描整棵树

导入阶段可以全量处理，但每一步导航必须局部读取。

## 7. GLM 必须执行的工作顺序

### 第一步：建立基线

先运行：

    npm test -- --run
    npm run build
    git diff --check

启动网页版，记录：

- 雨.lib 导入用时。
- 松月.lib 导入用时。
- 导入后打开棋谱用时。
- 连续前进 100 手总时间和最长单步时间。
- 打开分支面板时间。
- Chrome Performance 中超过 50ms、100ms、500ms 的长任务。
- 内存是否持续增长。

不要只凭手感，必须输出数据。

### 第二步：建立最小复现夹具

从真实 .lib 抽取：

1. 单条主线。
2. 一个节点 2 个分支。
3. 一个节点几十个分支。
4. 一个节点几千个分支。
5. 十万级子节点。
6. 含 ccc、c、黑/白/蓝标记的节点。
7. 连续多层分支。

每个夹具记录节点数、边数、分支数、最大子节点数、最大深度、直接子节点坐标、文字和标记字段。

### 第三步：确认 RenLib 数据模型

同时检查：

- 当前 RenLib 解析代码。
- 真实 .lib 十六进制数据。
- 爱五子棋打开同一文件的显示。
- 原软件导出的 SGF/文本（如果能获得）。
- 公开 RenLib 说明、开源解析器和测试样本。

输出字段表：

| 原始字段 | 当前解析位置 | 原软件显示 | 网页显示 | 是否确认 |
|---|---|---|---|---|
| 节点边界 | | | | |
| 父子关系 | | | | |
| 落子坐标 | | | | |
| 颜色 | | | | |
| board text | | | | |
| mark/control byte | | | | |
| 注释 | | | | |

### 第四步：比较架构

至少实际比较以下方案，而不是认定当前 Proxy 是最终答案：

A. 当前紧凑索引 + lazy facade。

B. 纯 nodeIndex 架构：UI 只保存整数 nodeIndex，子节点通过 childAt(index, offset) 读取。

C. 虚拟列表：分支面板只渲染视口附近行，不能让几万条分支变成 DOM。

D. 增量棋盘：父子导航增量放置/撤销，或使用可靠 board cache。

E. Worker 查询：大型分支查询、文字查询、统计和变体预览放 Worker。

可组合方案，但要记录每种方案的优劣和实测数据。

## 8. 性能验收标准

请在当前机器记录真实数据，尽量达到：

- 导入期间不阻塞 UI，进度持续更新。
- 导航单步通常小于 16ms，偶发不超过 50ms。
- 连续 100 步导航没有超过 500ms 的同步阻塞。
- 打开分支面板目标小于 100ms。
- 十万级分支只创建视口内 DOM。
- 读取一个直接子节点不应随总节点数线性增长。
- 关闭/打开面板后内存不持续泄漏。
- 不在 React render 中做大规模同步工作。

达不到时不能降低标准宣布完成，要继续尝试其他架构。
