## 1. 用户最终目标

用户真正关心的是：

> 导入大型 RenLib 棋谱后，软件仍然不卡顿，可以正常显示主线、所有分支和分支层级；分支面板可以打开和滚动，走到分支末端可以查看兄弟变化，刷新后可以恢复，软件体积不能明显膨胀。

严格验收还包括：

1. 不丢主线、分支、父子关系和兄弟关系。
2. 当前局面只显示直接后续变化点。
3. 已落子点不被后续标签覆盖。
4. 分支面板不按总分支数创建 DOM。
5. 导航通常小于一帧，不能出现明显卡死。
6. 大型文件导入、打开、导航、刷新恢复可重复验证。
7. RenLib 的 `ccc`、`c`、黑/白/蓝点不能凭猜测解释。

## 2. 已完成的主要改造

### 2.1 Worker 与大型文件

相关文件：

- `src/record-import.worker.ts`
- `src/formats.ts`
- `src/compact-index.ts`
- `src/App.tsx`
- `src/large-storage.ts`
- `src/types.ts`

已经完成：

- `.lib` 导入放入 Worker。
- Worker 不再把完整 `GameDocument.nodes` 作为最终结果回传主线程。
- Worker 返回元数据、警告和 `CompactRenLibIndex`。
- 主线程用 `createLazyDocument()` 重建兼容的 lazy document。
- compact index 保存：
  - parent
  - firstChild
  - nextSibling
  - childCount
  - preferredChild
  - moveCode
  - anchorCode
  - state
  - textRefs / texts
  - marks / markRefs
  - evaluation / evaluationLevel
- compact index 版本已升级为 2。

**重要诚实说明：**

当前 `src/formats.ts` 的 RenLib 解析仍然是：

```text
RenLib 流
  -> 中间 GameDocument.nodes
  -> buildCompactRenLibIndex()
  -> lazy document
```

也就是说，虽然 Worker 到主线程的完整对象树传输已去掉，但解析阶段仍会先构造一次完整 JS 对象树。它不是完全意义上的“直接 typed-array 解析”。如果 GPT 要继续优化，最有价值的方向是让解析器直接写入 compact arrays 和字符串池，彻底跳过中间 `GameDocument.nodes`。

### 2.2 分支面板与棋盘变化点

新增/使用的 compact API：

- `compactNodeIndex`
- `compactChildCount`
- `compactChildAt`
- `compactChildWindow`
- `compactSearch`

大型 lazy 文档的分支面板不再使用：

```ts
branchView.children.slice(start, end)
```

棋盘变化点也不再使用：

```ts
pivot.children.slice(0, 513)
```

当前行为：

- 保留完整分支总数。
- 固定窗口渲染可见分支。
- 最多只物化视口附近的分支节点。
- DOM 数量不随总分支数线性增长。
- 叶节点可以直接查看父节点的兄弟变化。

### 2.3 查找与导航

已经完成：

- 大型 lazy 文档查找使用 `compactSearch()`。
- 命中后才物化节点。
- 避免在 React render 中对大型文档执行 `Object.values(document.nodes)`。
- `Board` 组件使用 memo 化，减少导航无关状态引起的 SVG 重绘。
- `boardAt()` 增加父节点棋盘缓存：
  - 父棋盘已有缓存时，浅复制父棋盘并落当前一步。
  - 只有父棋盘未缓存时才回退到路径重放。
- 导航时清除待放置标签，避免标签跨节点或跨棋谱误写。

## 4. 当前最大问题

### 4.1 RenLib 仍不是完全直接 compact 解析

当前仍有中间完整对象树：

```text
importRenLib()
  -> createDocument()
  -> document.nodes[id] / children
  -> buildCompactRenLibIndex()
```

对 131 MB 的 `松月.lib`，使用普通对象树进行外部枚举曾触发：

```text
RangeError: Too many properties to enumerate
```

这说明真正彻底的解决方案仍应是：

```text
RenLib 流
  -> Worker 直接写 typed arrays
  -> 字符串池
  -> parent/firstChild/nextSibling
  -> ImportStats
  -> IndexedDB
```

不要再创建完整 `RecordNode` 和 `children` 数组。

### 4.2 `ccc`、`c`、颜色标记没有证据闭环

当前已确认的事实：

- 项目能读取部分 RenLib 控制位、注释和局面文字。
- 代码保留 `renLibMark` 和 `startPosition`。
- 用户观察到爱五子棋中存在黑点、白点、蓝点、`c`、`ccc`。

当前不能确认：

- `ccc` 是否原始字符串。
- `ccc` 是否由字节错位产生。
- `c` 属于哪个字段。
- 黑/白/蓝点对应哪个二进制字段。
- 爱五子棋显示颜色与 RenLib 字段如何对应。

**禁止：** 把这些内容硬编码为好手、坏手、败点、推荐点。

如果无法获得原软件导出或独立格式资料，应继续原样保留为未知字段，并在 UI 中明确“未知 RenLib 原始标记”。

### 4.3 `松月.lib` 完整结构统计仍不完整

`雨.lib` 已有完整统计，但 `松月.lib` 仍未取得可信的：

- 节点总数
- 边数
- 分叉节点数
- 最大子节点数
- 最大深度

原因是解析器本身仍创建完整对象树，在浏览器侧出现属性枚举限制。

最优解是直接 compact 解析时同步计数，而不是继续对 `document.nodes` 使用 `Object.keys/values`。

### 4.4 大谱导入时间仍很长

`松月.lib` 黑盒导入约 48.5 秒。

当前导入不会把页面卡死，但导入期间进度 UI 仍可能被浏览器的文件处理/Worker 数据传输影响。应记录：

- Worker 纯解析时间
- compact 构建时间
- IndexedDB 写入时间
- 主线程收到结果时间
- 页面 Long Task 时间

不要只报告总导入时间。

### 4.5 黑盒分支断言不够强

`qa/large-lib-blackbox.mjs` 已覆盖：

- 导入
- 100 步前进/后退
- 分支面板打开
- 滚动
- 刷新恢复
- DOM
- Long Task
- 控制台错误

但必须进一步确认：

- 面板显示的分支总数是否准确。
- 面板内是否确实存在分支按钮。
- 滚动后是否出现新窗口行。
- 点击某个兄弟分支后 current node 是否变化。
- 叶节点是否可以直接切换兄弟变化。
